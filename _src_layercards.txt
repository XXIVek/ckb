===SUMMARY
Первая карточка слоя правил MCP `1c-configurations-export` — уровень 2 дерева правил. Она говорит, что это за сервер и
как устроены правила его слоя; сами правила лежат следующим уровнем.

Сегодня правила слоя записаны под прежним адресом `export-rules:<...>` — слой ещё не переразвёрнут в
дерево `rules:export-rules:<правило>`. Поэтому перечень `===LINKS` ниже ведёт именно туда, а
подсказка «когда нужен» взята из раздела `===WHEN` самой карточки. Когда слой переразвёрнут,
ссылки переставляются на адреса дерева в тот же момент, когда меняется строка БД.

Раздел `===MCP` — общие записи слоя, перенесённые из корневой карточки без правок текста. Их разбор
по отдельным правилам и частям `ref:NNN` — отдельный шаг.

===MCP
### 📤 Шаг 4: Экспорт изменений конфигурации (MCP `1c-configurations-export`)

**Статус: сценарий не реализован** (узел V18). Таблица объектов конфигурации
(`configuration_objects`) с узла V33 **есть**, но это индекс состава по `ConfigDumpInfo.xml` —
без их XML; отслеживания изменённых объектов нет, поэтому выгружать в файлы нечего. Чтобы MCP не
обещал лишнего, в сервере оставлен один честный инструмент:

| Сценарий | Инструмент | Описание |
|----------|-----------|----------|
| Готовность экспорта | `export_readiness_tool()` | показывает, каких таблиц не хватает и сколько объектов в базе; вместо шести неработающих инструментов |

Удалены: `mark_object_modified_tool`, `clear_modified_flag_tool`, `get_modified_objects_tool`,
`count_modified_objects_tool`, `export_config_changes_tool`, `get_export_log_tool` — их таблица
`modified_objects` в схеме отсутствует. Что потребуется для V18: таблица объектов конфигурации с их
XML, флаги изменённых объектов, сборка XML по схеме и сравнение с выгрузкой.

### 4. Редактирование кода MCP `1c-configurations-export` (server_configurations_export.py)

**Перед началом редактирования файлов MCP `1c-configurations-export`:**

✅ **ОБЯЗАТЕЛЬНО** ознакомьтесь с файлом правил:

```text
C:\1C_LLM\ckb\.clinerules\1c-configurations-export_Rule.md
```

**Что нужно знать из файла правил:**

- Сценарий экспорта **не реализован** (узел V18): в схеме нет объектов, изменяемых в базе,
  и нет таблиц `modified_objects`, `config_export_log`. Таблица `configuration_objects`
  с узла V33 **есть** (перечень объектов метаданных по индексу состава, без их XML) —
  в перечне отсутствующих таблиц её быть не должно
- Контракт сервера — один инструмент `export_readiness_tool()` (диагностика готовности)
- Что требуется для появления экспорта: таблица объектов конфигурации с их XML, отслеживание
  изменений, сборка XML по схеме и сравнение с выгрузкой
- Штатный рабочий цикл сегодня: правки в файлах выгрузки → повторная загрузка
  `load_1c_catalog_tool(..., force=True)`

**После ознакомления:**

1. Убедитесь, что не возвращаете удалённые инструменты цикла (mark/count/export/clear)
2. Проверьте готовность живым `export_readiness_tool()` и составом через
   `python tools/check_mcp_tool_wiring.py`
3. Только после этого приступайте к редактированию кода

##### id=6106 rules:reserved:layer-migration tags=['1c-rules-root', 'rules', 'rules-layer', 'reserved']
===WHEN
Когда берёшься править правило core-rules, enrich-rules или export-rules.

===TRIGGER
Первый узел, который меняет правило одного из этих слоёв: править снимок нельзя — правило
пишется заново в формате v2 (rules:always:authoring), а прежний текст переводится в состояние
journal инструментом tools/readdress_rules_layer.py. Готового текста правил этих слоёв в формате
v2 нет, и выдумывать его без узла-причины значит написать правило, которого никто не проверял.

===WHERE
Прежние правила — под текущими адресами этих слоёв (формат 1), их исходники лежат в docs/rules.
Нормативы, на которые они ссылаются: docs/config-scenarios/FLOWCHART_1c-configurations-core.md и
docs/CONFIGURATIONS_ENRICHMENT_PLAN.md. Порядок перевода: readdress_rules_layer.py → авторинг
карточек v2 → tools/regen_journal_index.py → check_rules_layer.py --layer <метка>; что делает
последний шаг и почему он обязателен — rules:checks:layer-verification.
