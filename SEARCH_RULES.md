## АЛГОРИТМ ПРИНЯТИЯ РЕШЕНИЙ ПРИ ПОИСКЕ

### Шаг 1: Определение типа запроса

| Тип запроса | Пример | Что искать первым |
|-------------|--------|-------------------|
| Конкретный метод/функция | Как создать Справочник, Метод Random() | `search_docs_tool("Справочник")` |
| Пример кода/решение | Обработка исключений, HTTP-запрос | `search_docs_tool("обработка исключений")` |
| Общая информация | Что такое регистр | `search_docs_tool("регистр")` |

### Шаг 2: Приоритет поиска (внутри search_docs_tool)

1. **Поиск по алиасам (rank 3.0):** Точное совпадение LOWER(alias_name). Алиасы, привязанные напрямую к `snippets_id` без группы, получают приоритет rank=3.0 > групповых (rank=2.0)
2. **Full-text поиск по groups (rank 1.0):** Ищет по `name || pagetitle`. **heading НЕ участвует!**
3. **Full-text поиск по snippets (rank 0.5):** Ищет по `question || answer`
4. **Результаты сортируются по rank DESC**, limit применяется в конце.

### Шаг 2b: что именно возвращает поиск (критично для вывода)

`search_docs_tool` возвращает **список найденных строк: тип, ID, заголовок и превью в 200
символов** (`src/mcp_tools_api.py::search_docs`, поля `title[:200]` и `description[:200]`).
Полного содержимого в выдаче нет ни у групп, ни у сниппетов — это намеренно: `groups.description`
хранит весь `<body>` HTML, ответ ручного сниппета доходит до десятков килобайт.

Отсюда правило чтения результатов:

| Тип строки | Как получить содержимое | Статус |
|---|---|---|
| группа (`type=group`) | `get_doc_tool(doc_id)` — `pagetitle`, `title`, `heading`, `versionInfo`, `description` | работает |
| сниппет (`type=snippet`) | `get_snippet_tool(snippet_id)` — `question`, `answer`, теги, `confidence`, `is_verified`, `source_url`, родительская группа, алиасы с полным счётчиком, признак карантина и его причина | закрыто узлом P6, 20.10.2026 |

Обе фазы обязательны. Второй фазы без первой не бывает: `get_doc_tool` и `get_snippet_tool`
работают по ID, а ID даёт только поиск. Первой фазы без второй бывает вывод неверный: утверждать по
превью в 200 символов, что говорит вся строка, — значит выдавать недоказанное, потому что в выдаче
видно начало, а не словарь значений, не таблицу и не вывод. Поэтому вывод о полном тексте делается
по второй фазе, а не по превью.

Порог усечения ответа назван в каждом контуре своей константой: в `local_doc` это
`MAX_ANSWER_CHARS` = 8000 символов (`src/mcp_tools_api.py`, константа MCP-сервера), в контуре
выгрузок 1С — `MAX_ANSWER` = 8000 (`server_configurations_enrichment.py`); у загрузчика PDF
(`src/its_pdf_loader.py`) своя константа `MAX_ANSWER` = 6000 — она ограничивает длину сохраняемого
текста раздела, а не выдачу инструмента, путать их нельзя. `get_snippet_tool` отдаёт `answer_chars`
(полную длину) и `answer_truncated`; `get_doc_tool` печатает строку «ОПИСАНИЕ усечено до N символов
(полная длина M)». Обрезанный текст и текст целиком — разные ответы, и различие обязано быть
названо: без него усечённый ответ читается как полное содержимое строки.

### Шаг 3: Интерпретация результатов

Если найдены группы:

1. Проверяем tags — категория документа (language, platform, bsl, methodology, its, xml-format)
2. Смотрим pagetitle — официальное название из документации
3. Получаем полный HTML-контент страницы инструментом `get_doc_tool(doc_id)`, а не по превью
4. Проверяем versionInfo — с какой версии доступно

Если найдены сниппеты:

1. **Проверяем groups_id:**
   - `groups_id IS NOT NULL` → сниппет привязан к BSL-группе, полный контекст группы берётся
     из `get_doc_tool(doc_id)` этой группы
   - `groups_id IS NULL` → сниппет без группы (PDF, ручные, слой `xml-format`), контекста группы
     нет, и содержимое строки недоступно ничем, кроме как описано в Шаге 2b
2. Смотрим confidence — уверенность извлечения кода (0.5-1.0)
3. Анализируем question — контекст использования (он отдаётся целиком в пределах 200 символов)
4. **Содержимое сниппета (`answer`) из выдачи поиска не берётся**: там только превью. Полный текст
   читается второй фазой — `get_snippet_tool(snippet_id)`; вывод о строке по превью не делается

### 2b. Чтение и правка сниппета (узел P6, 20.10.2026)

```python
get_snippet_tool(snippet_id=4604)
# Вторая фаза двухфазного чтения: question и answer целиком (answer — до MAX_ANSWER_CHARS, с
# answer_chars и answer_truncated), теги, confidence, is_verified, source_url, created_at /
# updated_at, groups_id и родительская группа (id, name, pagetitle), алиасы строки с полным
# счётчиком aliases_total, признак карантина marked / marked_reason.
# Нужен затем: по превью поиска нельзя судить о словаре значений, таблице или выводе строки,
# а по числу алиасов — о её находимости («нет алиаса — знания для поиска нет»).

update_snippet_tool(snippet_id=4604, new_answer="…", reason="что и почему исправлено")
# Правка существующей строки с историей: прежнее содержимое уходит в snippet_audit_log
# (action=fix, полная копия old_question/old_answer). Необязательные параметры new_question /
# new_answer / tags / aliases меняются выборочно; reason обязателен; ни одного изменения — отказ, иначе пустая
# правка попала бы в аудит. tags заменяются целиком, но состояние карантина сохраняется
# (src/quarantine.py): правка текста не имеет права ни снять, ни поставить пометку; пустой набор
# тегов отклоняется — снять тег категории значит сделать строку невидимой для поиска с category.
# Алиасы удалять нельзя никогда: переданные aliases добавляются аддитивно, прежние остаются.
# Всё в одной транзакции: содержимое, алиасы, аудит — либо всё, либо ничего.
```

Почему правка — отдельный инструмент, а не «добавить новую строку»: `add_snippet_tool` создаёт
запись и оставляет старую, поэтому в базе остаются два противоречащих знания, и поиск отдаёт обе
строки. Так 20.10.2026 появились две карточки одного свойства с разными словарями значений.
Снять строку по-прежнему можно только пометкой к удалению (`mark_snippet_for_deletion_tool`,
узел Q1), физическая чистка — `tools/purge_marked_snippets.py`.

## ПРИОРИТЕТ И МЕХАНИКА ПОИСКА (приведено 20.10.2026 к коду `src/mcp_tools_api.py::search_docs`)

Здесь описана механика, а не пересказ кода: что именно сравнивается, по каким полям и что при этом
остаётся невидимым. Строки «алиас ищется по подстроке» и «полнотекстовый поиск ранжирует по
релевантности» — обе неверны; ниже то, что делает реализация.

### Три шага поиска — по порядку запросов

| Шаг | Таблица | Условие | rank |
|---|---|---|---|
| 1. алиасы | `alias_targets` | `LOWER(alias_name) = LOWER(<весь запрос>)` и `active = true` | `3.0` — алиас на сниппет; `2.0` — алиас на группу |
| 2. группы | `groups` | `to_tsvector('simple', name || ' ' || pagetitle) @@ to_tsquery('simple', <префикс>)` | `1.0` |
| 3. связанные сниппеты | `knowledge_snippets` по `groups_id` найденных групп | только для строк, найденных на шаге 2 | `2.0` |
| 4. сниппеты | `knowledge_snippets` | `to_tsvector('simple', question || ' ' || answer) @@ to_tsquery(...)` | `0.5` |

Итоговая выдача отсортирована по `rank DESC`, `limit` применяется в конце. Отдельного счёта
релевантности поверх этих чисел нет: `ts_rank` участвует только в порядке строк внутри своего шага,
поэтому строка с рангом `0.5` не может обойти строку с `3.0`.

### 1. Алиасный шаг — только точное совпадение всего запроса

Сравнивается вся строка запроса с `alias_name` целиком. Подстроки, части слова и формы падежа не
работают: `средн` не находит алиас `средний возраст`, `возраст` находит; `СреднийВозрастОС` находит
`среднийвозрастос` (регистр не учитывается), но не `средний возраст`. Многословный запрос в этот шаг
попасть не может в принципе и уходит в полнотекстовый с рангом `0.5–1.0`.

Практическое следствие, важнее самого ранжирования: **находимость термина в категории создаётся его
алиасами.** Строка без алиаса в нужной категории для поиска не существует, сколько бы текста о ней
ни лежало в базе. Карточка знания (свойство, идентификатор, ошибка) без набора алиасов — XML-имя,
имя колонки БД, русская формулировка, аббревиатура, обе формы с косой чертой и без — считается
незаписанной. Алиасы к существующей строке добавляет `add_aliases_tool` (число не ограничено,
дубликаты не создаются); `add_snippet_tool` генерирует их из вопроса, но не более 10.

### 2. Полнотекстовый шаг — поля, конфигурация, чего он не берёт

Индексируются не все тексты строки:

- `groups`: `name` и `pagetitle`. `heading` и `description` в выражении поиска не участвуют —
  `description` содержит весь `<body>` HTML, `heading` служит только для генерации алиасов;
- `knowledge_snippets`: `question` и `answer`.

Конфигурация текстового поиска — `simple` (для `question || answer` — `russian` там, где она явно
выбрана загрузчиком). Что из этого следует на практике:

- слова не лемматизируются: форма слова в запросе обязана совпадать с формой в тексте;
- идентификатор с подчёркиванием — одна лексема: `main_mode` не ищется по `configurations.main_mode`
  (точка разрывает токен);
- смешанная кириллица-латиница — тоже одна лексема (замер 20.10.2026, `C:\TMP\_p6_fts_probe.sql`):
  карточка со словами «Основной режим» не находится по запросу «Режим работы» и наоборот, потому что
  `Основной` и `режим` разнесены по разным концам токена;
- подстрока и середина идентификатора недоступны: `pg_trgm` в кластере не установлен. Середина ищется
  через `position()` в SQL-сверках либо через алиасы.

### 3. Фильтр по категории

`category` реализован 15.10.2026 (потребовался слою «профили свойств внешних объектов») и применяется
ко всем четырём шагам. Принимает один код или несколько через запятую; условие — пересечение массивов
тегов (`&&`), оно обслуживается GIN-индексами `idx_groups_tags` и `idx_snippets_tags`.

Категория наследуется: строка относится к категории, если её код есть в собственных тегах **или** в
тегах родительской группы. У BSL-сниппетов тег категории стоит на группе, и фильтр только по своим
тегам отдавал бы группы, теряя их сниппеты.

Строки без тега категории при запрошенной категории не отдаются вовсе — в этом и смысл изоляции слоя
знаний от общей документации. Пустой ответ с категорией означает «в этой категории термина нет»;
есть ли он в других категориях — проверяется запросом без `category`.

### 4. Пустая выдача: что она значит и чем лечится

| Что вернулось | Что это значит | Что делать |
|---|---|---|
| пусто с указанной `category` | в этой категории термина нет | повторить без `category`; искать в других категориях |
| пусто без категории | алиаса с таким написанием нет ни у одной строки | записать знание и его алиасы (`add_snippet_tool`, `add_aliases_tool`), а не перебирать формулировки запроса |
| есть только группы, сниппетов нет | у найденной группы нет сниппетов или они помечены к удалению | `include_marked=True`, чтобы увидеть карантин и причину |
| есть строка, но не та | запрос ушёл в полнотекстовый шаг, потому что с алиасом не совпал | переписать запрос одним термином в точной форме алиаса |

Формы одного термина — разные алиасы: `/DumpIB` и `DumpIB`, `ubound` и `убound`, XML-имя свойства
`DefaultRunMode` и его русское название. Искать надо тем именем, которым знание записано; если ни одна
форма не нашла — знания в базе нет.

### 5. Чего в этом контракте нет (границы, а не пропуски)

| Потребность | Состояние |
|---|---|

### Механика в один текст

```text
Запрос целиком == alias_name            → ранг 3.0 (алиас на сниппет) / 2.0 (алиас на группу)
tsvector('simple', name || pagetitle)  → ранг 1.0   (heading и description не ищутся)
связанные сниппеты найденной группы    → ранг 2.0
tsvector('simple', question || answer) → ранг 0.5
category (если указана)                → фильтр по тегам строки ИЛИ родительской группы, ко всем шагам
sort by rank DESC, then limit          → релевантность ts_rank над рангом не перетасовывает

выдача: ID + заголовок + превью 200 символов (не содержимое)
содержимое группы:  get_doc_tool(doc_id)            (description усекается до MAX_ANSWER_CHARS, это пишется)
содержимое сниппета: get_snippet_tool(snippet_id)   (answer до MAX_ANSWER_CHARS, отдаёт answer_chars/answer_truncated)
правка сниппета:     update_snippet_tool(..., reason) → строка меняется, прежнее уходит в snippet_audit_log
пусто с категорией = в категории термина нет; «алиаса нет» = знания в базе нет
```

## ⚠️ ЧАСТЫЕ ОШИБКИ И КАК ИЗБЕЖАТЬ

Ошибка: Использование таблиц search_aliases / docs / doc_fragments
Эти таблицы НЕ СУЩЕСТВУЮТ! Использовать alias_targets и groups.

Ошибка: Поиск только по name
search_docs_tool ищет по: name || pagetitle (groups) + question || answer (snippets). heading НЕ участвует в full-text поиске — только для генерации алиасов.

Ошибка: Игнорирование category
Если знаете категорию — всегда указывайте:

search_docs_tool(query="HTTP", category="platform") — быстрее и точнее
search_docs_tool(query="Random", category="language,bsl") — BSL-функции

Ошибка: Не проверка versionInfo
Всегда проверяйте versionInfo для совместимости!

Ошибка: Понимание группировки сниппетов
Сниппеты без groups_id (NULL) не связаны с группами. Они ищутся только по алиасам или full-text поиску. При поиске алиаса такие сниппеты получают приоритет rank=3.0.

Ошибка: Использование русских символов для алиасов
Алиасы генерируются из ASCII (pagetitle/heading). Используйте "ubound", а не "убound".

Ошибка: Считать, что содержимое сниппета видно из выдачи поиска
Выдача содержит превью в 200 символов. Утверждать по нему о словаре значений, таблице или выводе
— значит выдавать недоказанное. Содержимое группы читается `get_doc_tool(doc_id)`, содержимое
сниппета — `get_snippet_tool(snippet_id)` (узел P6, закрыт 20.10.2026): ID даёт поиск, вывод
делается по полному тексту второй фазы. Порог усечения `MAX_ANSWER_CHARS` обязан быть назван вместе с
полной длиной — усечённый ответ не выдаётся за полный.

Ошибка: Искать термин, которого нет среди алиасов, и считать это «знания нет»
Находимость строки в категории создаётся её алиасами: строка без алиаса в этой категории для
поиска не существует. Карточка знания без алиасов (XML-имя, имя колонки БД, русская формулировка)
считается незаписанной, даже если текст в базе есть.

Ошибка: Писать число сниппетов, алиасов или категорий без замера
Число без даты и без имени инструмента (`get_db_state_tool()`, `list_categories_tool()`,
`tools/count_snippet_breakdown.py`) устаревает молча — текст правил 07.10.2026 держал счётчики
ниже живых и четыре категории вместо пяти.

Ошибка: Делать вывод о знании по одному источнику, не прочитав его
Если найденные строки противоречат друг другу (например, разные словари значений одного свойства),
противоречие надо назвать и разрешить по авторитетному источнику (группа BSL-документации), а не
выбрать ту строку, которая первая попала в выдачу.
