### П2. Функции core-слоя как реестр реализованных функций со ссылками на журнал (предложение оператора, 28.10.2026)

Общая цель MCP `1c-configurations-core` — загрузка, редактирование и выгрузка конфигураций,
расширений, внешних отчётов и обработок. Функциональный слой обязан отражать, какая функция
завершена, а какая нет, и где смотреть историю её разработки.

1. **Ф-1. Инвентаризация функций.** Матрица: операции (загрузка / редактирование / выгрузка) ×
   виды объектов (конфигурация, расширение, внешний отчёт, внешняя обработка). Источники истины:
   `EXPECTED_TOOLS`/`DELETED_TOOLS` в `tools/check_mcp_tool_wiring.py`, узлы V в коде,
   `docs/CONFIGURATIONS_ENRICHMENT_PLAN.md`, `docs/EXTERNAL_OBJECT_EDIT_PLAN.md`.
2. **Ф-2. Карточка стадий** `rules:core-rules:functional:goal-and-stages`: состояние каждой
   ячейки матрицы (реализовано / частично / не реализовано / снято), дата, число инструментов до
   и после, ссылка на узел журнала. Карточка состояния `functional`, НЕ `always` — иначе будет
   нарушен `ALWAYS_BUDGET_CHARS` = 16 000 симв. (текущий always-core: 7090 + 1533).
3. **Ф-3. Ссылки на историю в каждую функциональную карточку.** Раздел истории
   (`===SOURCE===` в существующем формате) обязан называть **разрешимые адреса**
   `rules:core-rules:journal:node:vNN`, а не прозу «узлы V9, V22». Цель: 18/18 узлов разработки
   покрыты ссылками вместо 1/18; прозаические упоминания номеров узлов заменяются адресами.
4. **Ф-4. Недостающие узлы журнала.** Добавить `journal:node:v44` (модули предопределённых
   программ корня), `journal:node:v45`, узел о снятии инструментов правил (реестр 24.10.2026,

   узла здесь и есть незакрытая история.

### П3. Шаг чтения журнала в карточках правки кода

В четырёх `rules:<слой>:functional:edit-mcp-code` — шаг «перед правкой читают

## 4. Границы, которые план не меняет

1. **Журнал — снимок, а не правило.** Ссылка функции на узел журнала — указатель
   прослеживаемости; правило обязано оставаться самодостаточным, его текст не переносится в
   функцию из журнала.
2. **Источник текста подслоя — генератор.** `_make_layer_rule_cards.py` (core/enrich),
   `_make_rule_cards.py` (root), `_make_tool_cards.py`; правка строк БД в обход генератора
   теряет источник.
3. **Бюджет `always`.** Новые карточки стадий и функций относятся к вариативным (`functional:`),
   порог `ALWAYS_BUDGET_CHARS` = 16 000 симв. не поднимается без замера.
4. **Числа только из своего прогона.** Любая цифра в этом файле — замер на дату; актуальную
   даёт `python tools/check_rules_layer.py`.

  («Об изменении состава инструментов пишут узел журнала…») остаётся без изменений; живая карточка
  при этом обязательна всегда, потому что именно она и есть действующее правило. **Мера:**
  провалом `_journal_code_history.py` считает только случай, когда имя изменения не читается в слое
  ни живой карточкой, ни узлом журнала; выдача различает носители отдельными колонками.
  Основание: журнал объявлен снимком и сознательно исключён из проверки достижимости
  (`tools/check_rules_layer.py:751`), поэтому он не может быть единственным носителем нормы;
  обратная сторона — в export-rules шесть снятых имён читаются живой карточкой
  `rules:export-rules:functional:removed`, и вердикт «не покрыто» по только журнальной мере был бы
  ложным провалом по существу. Не зависит от D3 и остаётся в П2-Ф-4: узлы `v44`, `v45` и о снятии
  инструментов правил — решения, которых живая карточка не описывает.
