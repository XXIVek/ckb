### П2. Функции core-слоя как реестр реализованных функций со ссылками на журнал (предложение оператора, 28.10.2026)

Общая цель MCP `1c-configurations-core` — загрузка, редактирование и выгрузка конфигураций,
расширений, внешних отчётов и обработок. Функциональный слой обязан отражать, какая функция
завершена, а какая нет, и где смотреть историю её разработки.

1. **Ф-1. Инвентаризация функций.** Матрица: операции (загрузка / редактирование / выгрузка) ×
   виды объектов (конфигурация, расширение, внешний отчёт, внешняя обработка). Источники истины:
   `EXPECTED_TOOLS`/`DELETED_TOOLS` в `tools/check_mcp_tool_wiring.py`, узлы V в коде,
   `docs/CONFIGURATIONS_ENRICHMENT_PLAN.md`, `docs/EXTERNAL_OBJECT_EDIT_PLAN.md`.
2. **Ф-2. Карточка стадий** `rules:core-rules:functional:goal-and-stages`: состояние каждой
   ячейки матрицы (реализовано / частично / не реализовано / снято), дата, число инструментов до
   и после, ссылка на узел журнала. Карточка состояния `functional`, НЕ `always` — иначе будет
   нарушен `ALWAYS_BUDGET_CHARS` = 16 000 симв. (текущий always-core: 7090 + 1533).
3. **Ф-3. Ссылки на историю в каждую функциональную карточку.** Раздел истории
   (`===SOURCE===` в существующем формате) обязан называть **разрешимые адреса**

## 4. Границы, которые план не меняет

1. **Журнал — снимок, а не правило.** Ссылка функции на узел журнала — указатель

   `_rules_check_snapshot.py` — раньше его не мерил никто.
4. **Числа только из своего прогона.** Любая цифра в этом файле — замер на дату; актуальную
   даёт `python tools/check_rules_layer.py`, а состав слоёв, always-набор и длины адресов —
   `python _rules_check_snapshot.py`.
5. **Дата — из замера, а не из памяти.** Дату в тексте узла, карточки или плана берут из
   `git show` коммита либо из системных часов прогона (`_rules_check_snapshot.py` печатает дату

   на 27.10.2026; массовая правка прежних дат — отдельная работа, не часть П4. Формат ссылки
