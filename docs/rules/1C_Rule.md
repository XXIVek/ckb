## 📚 Слой правил MCP (узел RULE-LAYER, 24.10.2026)

Правила четырёх MCP-серверов занимают в контекстном окне несоразмерное место, а нужны по запросу —
когда вызывают инструмент этого сервера. Поэтому полный их текст живёт **строками базы `local_doc`**
и читается адресно. В контексте остаётся только этот маршрутизатор: он даёт карту и обязывает
начинать с индекса нужного слоя.

Механика та же двухфазная, что и весь поиск по базе: выдача `search_docs_tool` содержит id и превью
в 200 символов, содержимое читается `get_snippet_tool(snippet_id)`. У карточек слоя алиасов нет
намеренно: адрес — это заголовок строки, и он разрешается **шагом заголовков слоя** (`rank = 3.0`),
который включается, когда запрос начинается со служебной метки (`core-rules:`). Совпадение с алиасом
в этом не участвует — алиасов у карточек нет, и адрес остаётся единственной границей слоя.

### Как читать правила конкретного MCP (два шага)

```text
1. search_docs_tool(query="<индекс слоя>", category="<категория слоя>", limit=50)
      → get_snippet_tool(id): таблица адресов слоя (адрес | исходник | раздел)
2. search_docs_tool(query="<адрес карточки>", category=..., limit=5)
      → get_snippet_tool(id): полный текст нужного раздела
```

`category` указывать обязательно: без неё адрес ищется по всей базе и рядом кладёт сниппеты
со стороны (замер 24.10.2026: `export-rules:index` без категории отдал 30 чужих строк). Служебная
метка в начале запроса (`export-rules:`) включает шаг заголовков — он возвращает все карточки слоя
разом и полезен для обзора; адрес при этом обязан совпадать с заголовком целиком.

### Карта слоёв: MCP → метка индекса → категория

| Слой | Читать индекс | Категория | Исходник текста | Формат карточек |
|---|---|---|---|---|
| общие правила проекта | `rules:index` | `rules` | `docs/rules/rules.md` | 2 — карточки-правила |
| `1c-knowledge-base` | `kb-rules:index` | `1c-knowledge-base` | `docs/rules/kb-rules.md`; прежний текст — журнал `kb-rules:journal:index` | 2 — карточки-правила |
| `1c-configurations-core` | `core-rules:index` | `1c-configurations-core` | `.clinerules/1c-configurations-core_Rule.md` | 1 — дословный перенос |
| `1c-configurations-enrichment` | `enrich-rules:index` | `1c-configurations-enrichment` | `.clinerules/1c-configurations-enrichment_Rule.md` | 1 — дословный перенос |
| `1c-configurations-export` | `export-rules:index` | `1c-configurations-export` | `.clinerules/1c-configurations-export_Rule.md` | 1 — дословный перенос |

Индекс слоя — первая карточка слоя (`<метка>:index`). У слоя формата 1 карточки нумеруются по
разделам исходника (`<метка>:ref:NN`), вторая и последующие части большого раздела —
`<метка>:ref:NN:2`. Слои `core-rules` и `enrich-rules` дополняют прежние журнальные карточки
(`core-rules: п. 30 ч. 1`, `enrich-rules: V17.12`) — они остаются под прежними заголовками, и
в индексе `core-rules:index` названо, где их искать.

### Состояния карточек (узел RULE-V2)

Адрес карточки формата 2 содержит состояние: `<метка>:<состояние>[:карточка]`. Формат карточки
требуют не все состояния — требование различается, и в этом смысл деления:

| Состояние | Что это | Что требуется | Чем читать |
|---|---|---|---|
| `always` | правила, применимые до любого действия слоя | разделы `WHEN/MUST/FORBID/TOOLS/CHECK/SOURCE`, бюджет слоя ≤ `ALWAYS_BUDGET_CHARS` | индекс `…:always:index` |
| `optional` | правила «по ситуации» | те же разделы | индекс `…:optional:index` |
| `checks` | чем доказывать, что правило ещё верно | те же разделы; в индексе каждой строки назван инструмент проверки | индекс `…:checks:index` |
| `reserved` | заявленное, но ещё не сформулированное | `WHEN/TRIGGER/WHERE`, длина ≤ `RESERVED_MAX_CHARS` | индекс `…:reserved:index` |
| `journal` | снимок прежних правил | формату не проверяется; тексты не правятся | индекс `…:journal:index` |

Снимок (`journal`) и заявка (`reserved`) — разные состояния намеренно: «правило было» и «правило
будет» одинаково не являются действующим правилом, но читаются по-разному. Правку состояния
описывает `rules:always:authoring`. Состояние без карточек объявляется в индексе слоя текстом, а
не молчанием: «проверок нет» и «проверок не нашли» — разные ответы.


### Инструменты слоя

| Скрипт | Что делает |
|---|---|
| `python tools/migrate_rules_to_layer.py --file docs/rules/<метка>.md --apply` | переносит файл слоя в строки `knowledge_snippets`: одна транзакция на слой (либо все карточки, либо ни одной), чужие слои не трогает, повторный прогон не размножает строки; `--all` — все файлы `docs/rules/`. Без `--apply` — только разбор и отчёт |
| `python tools/check_rules_layer.py --layer <метка>` | доступность и целостность слоя: индекс и каждая карточка разрешаются адресом, категория изолирует слой, текст строки БД совпадает с исходником, набор карточек слоя в БД равен набору в файле, у карточек нет алиасов и чужих меток, маршрутизатор называет индекс слоя (адресом, а не подстрокой), в БД нет строк слоя без исходника. Для формата 2 дополнительно: разделы карточек соответствуют состоянию, индекс состояния — таблица с названным инструментом проверки, каждая строка индекса разрешается в карточку, оглавление журнала перечисляет фактические карточки, бюджет `always` не превышен. Без `--layer` — все слои сразу |
| `python tools/plan_rule_sections.py --marker <метка> --source <файл>` | порождает `docs/rules/<метка>.md` из файла правил: разделы переносятся дословно, большой раздел дробится по подзаголовкам следующего уровня с закрытием и переоткрытием fenced-блока на границе части, крошечные куски склеиваются, оглавление пересобирается, рукописный блок между `<!-- hand:start -->` и `<!-- hand:end -->` сохраняется, карточки других слоёв (внешние ссылки) остаются нетронутыми |
| `python tools/readdress_rules_layer.py --layer <метка> --apply` | переводит карточки слоя формата 2 в состояния (переименование адресов): заголовок строки БД меняется, `source_url` (`rules-layer://<адрес>`) остаётся ключом идемпотентности, карточки других слоёв не трогает; без `--apply` — только план переименований |
| `python tools/regen_journal_index.py --layer <метка> [--write]` | перегенерирует оглавление журнала `<метка>:journal:index` по фактическому составу строк состояния `journal` в БД: после `readdress_rules_layer.py` прежнее оглавление перечисляет адреса до переименования, и ссылки ведут в карточки, которых нет. Тексты карточек журнала не меняются. Отбор карточек идёт тегами метки и `journal`, запись — в черновик `docs/rules/<метка>.md`, поэтому работает только там, где и теги, и черновик есть (корень `rules:`); подслою дерева инструмент отказывает («карточек журнала в БД нет — перегенерировать нечего», rc=1: карточки адресуются адресом, тегов и черновика у них нет), а его перечень `rules:<метка>:journal:index` правится скриптом, добавляющим узлы журнала, или строкой БД по адресу; слою формата 1 отказывает — оглавления журнала у него нет |
| `src/rules_layer.py` | общий разбор и проверка формата: у мигратора, плана и проверки один парсер и одна грамматика адреса (расхождение парсеров дало бы «проходит у одного, падает у другого») |

Границы формата — грамматика адреса `src/rules_layer.py::ADDRESS_RE`: латинская метка слоя и
латинские сегменты через `:`; адрес карточки не может быть префиксом другой карточки того же слоя,
поэтому части большого раздела различаются суффиксом `:2`, `:3`. Карточка обязана называться в
оглавлении своего индекса — иначе она есть в файле и не находится адресом.

### Что это меняет в порядке работы

1. Перед работой с MCP-сервером читаются индекс его слоя и нужные адреса, а не файл правил целиком.
   Файлы `.clinerules/*_Rule.md` пока остаются исходниками переноса и входами
   `tools/check_search_rules_sync.py` — снять их можно только вместе с переводом этой сверки на
   `docs/rules/*.md`.
2. Правка правила идёт парой: правится исходник (`docs/rules/<метка>.md`, а для слоёв, порождённых
   планом, — файл правил и перегенерация плана), затем `migrate_rules_to_layer.py --apply`, затем
   `check_rules_layer.py`. Правка только строк БД рассинхронизирует слой с исходником — сверка это
   ловит (правило «правим только в базе» здесь не отменяется: файл — исходник переноса, а не место
   правки поведения).
3. Новый слой заводится по той же схеме: `plan_rule_sections.py` → `migrate_rules_to_layer.py` →
   `check_rules_layer.py`. Каталог слоёв `LAYERS` (плюс `LAYER_FORMAT`, `LAYER_STATES`) — в
   `src/rules_layer.py`; метки префиксного шага поиска `TITLE_LAYER_MARKERS` — в
   `src/mcp_tools_api.py`. Оба набора обязаны совпадать: метка без записи `LAYERS` — мёртвый
   префикс, запись без метки — карточка, которая адресом не читается.

## ПРИНЦИП РАБОТЫ

### 📚 Шаг 1: Поиск документации (MCP `1c-knowledge-base`)

**Когда использовать:** При ответе на любые вопросы по языку BSL, платформе 1С, ИТС, методологии.

> ⚠️ **Шаг 0 поиска (принят 20.10.2026):** перед первым `search_docs_tool` — `get_search_rules_tool()`.
> Механика поиска неочевидна и без неё вывод строится на догадках: алиасный шаг работает только по
> **точному совпадению** всего запроса с `alias_name`, а выдача содержит **ID строки и превью в 200
> символов**, но не содержимое. Содержимое группы читается `get_doc_tool(doc_id)`; содержимое
> сниппета — `get_snippet_tool(snippet_id)` (закрыто узлом P6, 20.10.2026: выдаёт `answer` целиком
> до порога `MAX_ANSWER_CHARS` = 8000 с `answer_chars` / `answer_truncated`, алиасы, родителя,
> признак карантина). Правка сниппета — `update_snippet_tool` с обязательным `reason` и историей
> в `snippet_audit_log`; строка не дублируется. Вывод о полном тексте сниппета по превью не делается.
> Находимость термина в категории создаётся его алиасами:
> пустая выдача с категорией = в категории термина нет, а «алиаса нет» = знания в базе нет.
> Текст правил обязан совпадать с кодом — это сторожит `python tools/check_search_rules_sync.py`.

| Сценарий | Инструмент | Описание |
|----------|-----------|----------|
| **Правила поиска (Шаг 0)** | `get_search_rules_tool()` | механика поиска: алиасы = точное совпадение, двухфазное чтение (ID → содержимое), категории, пустая выдача |
| Правила загрузки документов | `get_load_rules_tool()` | правила загрузки HTML/PDF/Markdown в базу |
| Общий поиск по документации | `search_docs_tool(query, category?, limit?, include_marked=False)` | Комбинированный поиск по группам, сниппетам и алиасам; `category` фильтрует выдачу по категории (реализовано 15.10.2026); сниппеты, помеченные к удалению (узел Q1, тег `mark-for-deletion`), скрыты по умолчанию — `include_marked=True` отдаёт их с явной пометкой |
| Получить полную группу | `get_doc_tool(doc_id)` | Получить HTML-контент группы справки по ID |
| Прочитать сниппет целиком (узел P6) | `get_snippet_tool(snippet_id)` | Вторая фаза чтения сниппета: `answer` до `MAX_ANSWER_CHARS` (8000) с `answer_chars`/`answer_truncated`, алиасы с полным счётчиком, родительская группа, `marked`/`marked_reason` |
| Исправить сниппет с историей (узел P6) | `update_snippet_tool(snippet_id, new_question?, new_answer?, tags?, aliases?, reason)` | Правка существующей строки, а не новая строка: прежнее содержимое уходит в `snippet_audit_log` (`action=fix`); `reason` обязателен; теги карантина сохраняются; алиасы добавляются без дублей и никогда не удаляются |
| Проверить состояние БД | `get_db_state_tool()` | Узнать количество групп, сниппетов, алиасов |
| Список категорий | `list_categories_tool()` | Список категорий и честные счётчики по каждой (группы / сниппеты / алиасы) |
| Загрузить документацию | `load_doc_tool(path, category)` / `load_bsl_tool(path)` / `load_single_html_tool(filepath, category)` | Загрузка HTML/PDF/Markdown документов в БД |
| Добавить сниппет кода | `add_snippet_tool(question, answer, ...)` | Добавить вопрос-ответ с примером кода |

**Категории документации:**

- `language,bsl` — язык BSL (источник: `/html/BSL/`)
- `platform` — платформа 1С (источник: `/html/platform/`, PDF)
- `its` — ИТС (информационно-технологическая поддержка)
- `methodology` — методология программирования
- `xml-format` — формат XML-выгрузки метаданных: профили свойств внешних объектов
  (значение по умолчанию, допустимые значения, происхождение) — слой знаний, которым
  пользуется инструмент создания внешнего объекта; фильтр по категории работает

> **Важно:** ВСЕГДА начинай работу, связанную с 1С, с поиска в `1c-knowledge-base`. Только если нужной информации нет — переходи к анализу файлов вручную.

### ⚙️ Шаг 2: Загрузка выгрузок 1С (MCP `1c-configurations-core`)

**Когда использовать:** загрузить каталог выгрузки (внешний отчёт, внешняя обработка, конфигурация,
расширение) в базу `ckb_1c_configurations`, подтвердить перезагрузку дубликата, удалить загруженный
объект. **Смотреть содержимое объекта средствами core-MCP нельзя** — инструменты просмотра удалены:
для этого служат MCP `1c-configurations-enrichment` (карточка объекта, поиск по алиасам, сниппеты)
и SQL-сверки `check_external_report_*.sql`.

| Сценарий | Инструмент | Описание |
|----------|-----------|----------|
| Правила загрузки (Шаг 0) | `get_load_config_rules_tool()` | compact-правила `LOAD_RULES_Config.md` |
| **Загрузка каталога (точка входа каталога)** | `load_1c_catalog_tool(source_path, force=False)` | тип каталога определяется самим сервером по файлам корневого каталога |

### ⚠️ Критические правила работы с MCP

1. **ВСЕГДА начинай с `1c-knowledge-base`** — только если информации нет, переходи к файлам.
   Внутри этого шага есть свой Шаг 0: `get_search_rules_tool()` перед первым запросом (см. раздел
   «Шаг 1: Поиск документации»). Отдельное правило вывода: **не утверждать о том, что не читали.**
   Выдача поиска — ID и превью в 200 символов; о словаре значений, таблице или выводе строки по
   превью ничего не известно. Если противоречат друг другу две строки базы, противоречие называется
   прямо и разрешается по авторитетному источнику (группа BSL-справки), а не по порядку в выдаче.
2. **Исходники вне проекта:** `C:\1C_LLM\LoadDoc\` — документация и конфигурации
3. **Все MCP-инструменты работают через `server.py`, `server_configurations_core.py`, `server_configurations_enrichment.py`, `server_configurations_export.py`** — не напрямую через mcp_tools.py; состав инструментов каждого сервера зафиксирован в `tools/check_mcp_tool_wiring.py`
4. **psql.exe запускается по карточке правил:** полную строку с флагами `-tA -P footer=off`, путь к
   бинарю, `-U postgres` и реквизиты подключения называет `rules:kb-rules:functional:db-access` —
   читать `python tools/rules_read.py "rules:kb-rules:functional:db-access"`. Команда здесь не
   повторяется: вторая копия правила расходится с первоисточником молча (замер 07.11.2026 — в этой
   копии не хватало `-U postgres`, вызов падал на отсутствующей роли `Buh`)  
5. **Никогда не запрашивать подтверждение** на продолжение вывода — команды выполняются автоматически
6. **Фильтровать вывод:** использовать LIMIT, WHERE в SQL или [:10], head в Python
7. **Дубликат — спрашивать, а не решать самому.** Получив `⚠️ уже загружено`, AI-ассистент
   останавливается и спрашивает оператора; `force=True` без вопроса допустим только по явной
   команде «замени конфигурацию» / «перезагрузи» (правило R5, `LOAD_RULES_Config.md`)
8. **Никаких обращений мимо MCP при анализе содержимого объекта.** Не допускается `psql.exe`,
   `information_schema`, чтение файлов выгрузки ради ответа оператору — для этого есть
   инструменты контракта (`config_enrichment_stats_tool(card=True)`,
   `list_config_aliases_tool`, `list_config_snippets_tool`, `get_config_snippet_tool`).
   Прямой SQL и разбор файлов остаются только в скриптах-валидаторах и SQL-сверках проекта
9. **Обогащение завершается полностью, без напоминания:** после
   `generate_config_enrichment_tool` обязательно добавить ручные алиасы
   (`add_config_aliases_tool`) и указатели на документацию
   (`add_config_cross_reference_tool` по группам из `search_docs_tool`); `doc_links = 0`
   в карточке — признак незавершённой работы, а не повод предлагать это оператору.
   Указатели ставятся **по критериям T1–T3** (T1 — якорь на конкретный фрагмент: `Template`,
   `Module`, `Form`, сниппет; T2 — только неочевидное поведение и дефекты; T3 — не дублировать
   типовое для любого отчёта СКД, общие ссылки на языковой API по умолчанию не ставятся).
   Якорь обязан переживать перегенерацию: id авто-сниппетов меняются при каждом
   `generate_config_enrichment_tool`, поэтому ссылка на авто-сниппет гибнет — якорь берут на
   цель по имени (`Template`/`Form`/`Module`/`Attribute`) или на ручной `is_verified=true`.
   Полные формулировки — правило 9 `.clinerules/1c-configurations-enrichment_Rule.md`
10. **Правим только в базе данных (принято оператором 15.10.2026).** Создавать, редактировать и
   удалять внешние объекты мы можем **только строками БД** `ckb_1c_configurations`
   (`external_report`, `attributes`, `tabular_sections`, `forms`, `form_ext`, `templates`,
   `bsl_modules`, `config_*`). Каталог XML-выгрузки — **не источник истины и не место правок**: он
   нужен только как транспорт, через который объект загружается в БД
   (`load_1c_catalog_tool`, `load_external_object_file_tool`) и выгружается из неё
   (сборка XML из строк БД → `ibcmd config import` → `.erf`/`.epf`). Штатный цикл правки:
   **правка строк БД → сборка XML из БД → `import_from_layout` → проверка в конфигураторе →
   повторная загрузка**. Правки файлов выгрузки «в обход БД» рабочим путём не считаются.
   Следствие: любой инструмент правки обязан писать в БД, а отдавать объект наружу — только через
   сборку XML из этих же строк (узел V18/V29).

## РАБОТА С ТЕРМИНАЛОМ

Запуск psql.exe — по карточке правил, её читают адресом:

```powershell
python tools/rules_read.py "rules:kb-rules:functional:db-access"
```

В карточке — строка запуска с флагами `-tA` (тихий режим) и `-P footer=off` (выключенный
постраничный вывод), путь к бинарю `C:\Postgres\bin\psql.exe` (в `PATH` его нет), `-U postgres`
(роли `Buh` на сервере нет) и реквизиты подключения. Команда здесь не дублируется: две копии одного
правила расходятся молча, и в этой копии `-U postgres` уже не было — замер 07.11.2026.

Критические правила:

- Никогда не запрашивать подтверждение пользователя на продолжение вывода — команды с длинным выводом (psql, python) выполняются автоматически
- Не использовать `run_commands` с командами, выводящими много строк без фильтрации — использовать LIMIT, WHERE, выборочные поля
- Если результат большой: фильтровать на стороне SQL (`WHERE`, `LIMIT`) или Python (`[:10]`, `head`)
