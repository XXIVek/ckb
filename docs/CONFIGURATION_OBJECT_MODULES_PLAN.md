### 2.2 Что витрина делает с NULL-путём (проверено прогоном, а не рассуждением)

Правило текущей строки `v_current_bsl_modules` сравнивает `parent_uuid` и `file_path` и оставляет
строку, если для неё нет строки с большей `revision_no`. Прогон правила на четырёх строках
(`WITH m …`, id r1/r2 с `file_path IS NULL` в ревизиях 1 и 2, r3/r4 с реальным путём):

```
r1|u1|(NULL)|1
r2|u1|(NULL)|2
r4|u2|/x/Ext/ObjectModule.bsl|2
```

При NULL-путе проходят обе ревизии (`NULL = NULL` в SQL — не истина), при пути — только высшая.
Значит строка без пути после первой же перезагрузки конфигурации остаётся в текущем множестве во
всех ревизиях сразу. Вывод для узла при решении Q2 (раздел 5.2): строк для отсутствующих файлов не
заводится, поэтому **каждая строка таблицы имеет путь**, и пара `(parent_uuid, file_path)` остаётся
тотальной границей без правки витрины — имя файла несёт слот, поэтому модули одного владельца
различаются сами.

## 5. Решения оператора — до кода (задавать по одному)

**Q1 (схема) — решено оператором 28.10.2026: модули объектов живут в `bsl_modules`.**

Формулировка оператора: разница между объектом конфигурации и внешним отчётом (обработкой) в записи
модуля только в том, что у конфигурации uuid конфигурации и uuid объекта — разные, а при загрузке
внешнего объекта они совпадают и равны uuid отчёта; в остальном записи не отличаются. Одна таблица
даёт обогатить всю выбранную конфигурацию сниппетами в одном проходе.

Проверка схемы подтвердила: модель уже реализована узлом V46, а возражения против единой таблицы,
которые приводил ассистент, на машине не держатся.

| Проверенное | Что показывает |
|---|---|
| `pg_get_viewdef('v_current_bsl_modules')` | текущее состояние разрешается общим правилом `parent_uuid` + `file_path` + максимум `revision_no`, а не манифестом; правило одинаково для обоих контуров |

| прогон `_v46_p5_loader_probe.py` (раздел проверок «родитель каждой строки — uuid самого общего модуля», «parent_type называет таблицу-родителя, module_type — слот вида») | V46 пишет ту же модель для общих модулей: `parent_uuid` = uuid модуля, `parent_type='common_modules'`, `module_type='Module'` |

Вторая точка входа (`configuration_object_modules`) при этом означала бы два места для одного понятия
и лишила бы S5 единого прохода по модулям конфигурации — того, ради чего узел и делается.

Условия решения (технические, а не возражения — без них A не работает):

1. **Тотальность ключа — правило оператора (28.10.2026).** Любая строка `bsl_modules` обязана иметь
   заполненными `configuration_uuid` **и** `parent_uuid`; NULL хотя бы одного из них — это ошибка
   записи модуля. Значит обе колонки переходят на `NOT NULL`, а писатель отклоняет строку до записи,
   а не молча пишет половину ключа. Живые строки внешнего контура правилу уже не соответствуют
   (id 306, 307 — `configuration_uuid` NULL), поэтому миграция заполняет
   `configuration_uuid = parent_uuid` для `parent_type = 'external_report'`: это физическая запись
   модели оператора («у внешнего объекта оба uuid совпадают и равны uuid объекта»). Инвариант
   «строк с NULL в любом из двух uuid — 0» входит в проверку узла и в `check_v32_zero_configuration`.
2. **Конвенция `file_path`.** Ключом текущего состояния витрина уже выбрала пару
   `(parent_uuid, file_path)`. При `file_path IS NULL` правило выродится: строки разных ревизий
   перестанут различаться и останутся все сразу. V46 для `indexed_no_file` оставляет путь NULL
   (`common_module_sources_path_state_check`) — в `bsl_modules` так нельзя. Путь модуля объекта
   выводится из имени записи индекса и известен до обращения к диску, поэтому пишется **всегда**;
   отсутствующий файл строки не даёт вовсе (решение Q2 от 28.10.2026), поэтому конвенция
   «путь NULL при отсутствии текста» в этой таблице не появляется. Различие двух конвенций в двух
   таблицах называется в нормативах прямо.
3. **Колонка состояния не вводится** — прежний пункт требовал `code_state` с CHECK по контракту
   V44/V46, решение Q2 от 28.10.2026 это сняло: отсутствие строки означает пустой модуль,
   состояний `file` / `empty_file` / `indexed_no_file` / `undecoded` для модулей объектов в таблице
   нет. `truncated` остаётся для прежних строк и в новом контракте не участвует — это называется, а
   не переопределяется молча. Отличие от общих модулей V46 (пустой модуль остаётся строкой с
   `code IS NULL`) тоже называется прямо: CHECK на `code` не вводится, потому что он сломал бы
   контракт V46, — граница держится писателем и проверкой узла.
4. **Следствие для проверок.** `tools/check_v32_zero_configuration.py:452` считает
   `COUNT(*) FROM bsl_modules` как инвариант чистоты, `tools/check_v19_revisions.py:331`
   нормализует регистр пути ключа манифеста — обе переснимаются числами нового состава. Это
   следствие расширения таблицы, а не повод менять схему.


**Q2 (ключ строки и выражение состояния) — решено оператором 28.10.2026.**

Определение оператора: отсутствие модуля объекта (модуля менеджера, модуля объекта) не является
ошибкой — это норма при программировании в 1С. Если при поиске по uuid конфигурации и uuid объекта
запись в `bsl_modules` не найдена, это означает, что модули у объекта пустые. Если запись в таблице
есть — она обязана иметь путь. Колонка состояния для модулей объектов не вводится.

Чем это отличается от прежней постановки вопроса (и от контракта V44):

- строк для записей индекса без файла (замер — 47 в круге узла) не заводится вовсе: запись индекса
  состава сама по себе фактом о коде модуля не является;
- состояний `indexed_no_file` / `empty_file` / `undecoded` для модулей объектов в таблице нет, в
  отличие от контракта V44 для модулей корня. Различие двух контрактов в одном проекте называется
  прямо: у модулей корня граница сохранена (V44, `code_state` с CHECK), для модулей объектов её
  снимает решение оператора, потому что пустой модуль — штатное состояние, а не исключение;
- `code_state` не добавляется; объём кода называется существующей колонкой `code_size`, пару
  `code_chars`/`code_bytes` в `bsl_modules` не заводим — иначе в одной таблице появится два способа
  измерить один код. Колонка `truncated` остаётся для прежних строк и новых не касается.

Граница ключа берётся та, которой уже принадлежит витрина, и править её не нужно:
`UNIQUE (parent_uuid, file_path, revision_no)`. Каждая строка имеет путь, поэтому граница тотальная,
а имя файла несёт слот — модули одного владельца различаются сами. `configuration_uuid` и
`parent_uuid` — `NOT NULL` по правилу оператора (пункт 1 раздела 5.1).

Открытая позиция **O1 — машинный код вместо исходника.** Оператор указал (28.10.2026): бывают
модули, где вместо `.bsl` лежит `.bin` — машинный код 1С, к которому разработчик прибегает при
защите модуля паролем или обфускации, то есть когда содержание модуля не хотят открывать посторонним.
Решение — вводить ли флаг или считать такой модуль пустым — отложено; на текущем этапе принимается,
что таких модулей нет. Замер (раздел 2.3) показывает противное: **18 записей круга узла** —
KomMag 9 (`ValueManagerModule`), BP3 5 и BGU2 4 (`ObjectModule`). Число названо, чтобы проверка П5 и
читатели не выдавали их за пустые молча. Имя для этого случая в проекте уже есть —
`content_state = 'bin_only'` узла V46 (4 записи общих модулей BGU2). Возврат к решению — отдельный
шаг, в круг V47 он не входит.

**Q6 (режим записи кода) — был открыт, закрыт решением ниже.** Замер раздела 2.3: весь код круга узла — **303.9 МиБ,
182 790 397 символов** (BP3 164.5 МиБ, BGU2 137.3 МиБ, KomMag 2.0 МиБ, MinCfg 0.2 МиБ). Вопрос в
том, ложится ли этот объём в базу при загрузке или текст поднимается с диска по запросу.

Прецедент задан решениями V46, и их надо назвать, а не обходить:

- **D6** — две таблицы: `common_module_sources` держит путь и размер вместо текста, содержимое пишет
  отдельная процедура, «чтобы `bsl_modules` не раздувался строками „текста нет“»
  (`docs/CONFIGURATION_OBJECT_PROPERTIES_PLAN.md`, строка D6);
- **D7** — две транзакции: коммит №1 (свойства, ссылки, дескрипторы) → чтение `.bsl` по путям →
  коммит №2 (`bsl_modules`); отказ второй стадии не откатывает первую и называется в ответе
  отдельно;
- флаг `with_module_content` по умолчанию `False` — потому в живой базе строк текста общих модулей
  нет: `content_loaded = false` у всех 2 378 дескрипторов (замер 28.10.2026);
- пустой модуль у V46 остаётся **строкой** с `code IS NULL` и `code_size = 0` («текста нет» и
  «файла нет» — разные состояния, `common_module_text_row`), а `bin_only` строки не получает,
  считается в `skipped`, путь `.bin` возвращается отдельным ключом `bin_path` для предупреждения.

Решение Q2 (пустой модуль объекта строки не требует) снимает главный аргумент D6 — раздувание
строками «текста нет»: таких строк узел не пишет вовсе. Остаётся только объём.

Варианты:

- **A. код пишется той же транзакцией, что и строки.** Просто, но противоречит D7: отказ чтения
  300 МиБ откатывал бы уже записанные строки;
- **B. строки — коммит №1, код — коммит №2 по флагу, как в D7.** Граница отказа сохранена:
  вызывающий видит «строки загружены, код модулей — нет», а не половину результата;
- **C. код в базу не пишется вовсе** — текущее поведение V46 по умолчанию. База не растёт, но
  обогащение модулей объектов невозможно без чтения вне базы, то есть это откат к той причине, из-за
  которой узел и поднят.

Реализация `undecoded` (оставался открытый пункт Q2). Отдельного состояния в таблице нет, но и молча
потерять модуль нельзя: файл, который не раскодируется, остаётся ошибкой стадии по правилу **C5**
закрытого контракта (`src/configuration_load_contract.py`: «файл модуля не раскодирован» — из того,
что останавливает конвейер). Замер круга даёт 0 таких файлов, то есть правило на текущих выгрузках не
срабатывает; при появлении такого файла загрузка остановится с текстом ошибки, а не потеряет модуль
без слова.

**Q6 (режим записи кода и место обогащения) — решено оператором 28.10.2026: вариант B, обогащение —
отдельный вызов.**

Определение оператора:

1. **обогащение всей конфигурации — отдельный вызов, а не часть загрузки.** Основание названо
   прямо: у загрузки жёсткое правило — при ошибке она останавливается с сообщением об ошибке, а
   повторная загрузка начинается со снятия уже загруженных данных; любое обогащение до конца
   загрузки означает риск впустую потраченных ресурсов и времени;
2. **режим записи кода — B**: содержимое конфигурации — первый коммит, модули объектов — второй
   транзакцией, то есть границей, заданной решением D7 узла V46.

Что из этого следует для узла:

- позиция оператора совпадает с уже записанным планом: S5 (анализ и снижение сниппетов) задана
  дополнением оператора от 23.10.2026, в `STAGES` её нет, план — раздел 16
  `docs/CONFIGURATIONS_ENRICHMENT_PLAN.md`, карточка `rules:core-rules:functional:goal-and-stages`
  называет её несогласованной. **Узел V47 S5 не реализует и обогащение не вызывает**: задача узла —
  чтобы код модулей объектов лежал в базе, а не чтобы он был обогатён в той же загрузке;
- граница двух транзакций для V47 означает: содержимое конфигурации (S1–S4) зафиксировано и остаётся
  зафиксированным, строки модулей объектов пишутся отдельной транзакцией после него; отказ модульной
  стадии не откатывает записанное и называется в ответе отдельно (смысл D7);
- **внутри второй транзакции каждая строка уже содержит код**: правило Q2 («строка есть ⇒ есть путь и
  есть код») не допускает промежуточного состояния «строка без кода». Дескрипторной таблицы для
  модулей объектов не заводится — роль дескриптора выполняет индекс состава
  (`configuration_objects`, запись слота), а «текста нет» выражается отсутствием строки. Отличие от
  V46 (дескриптор — отдельная таблица, пустой модуль остаётся строкой с `code IS NULL`) называется
  прямо и следует из решения Q2, а не из небрежности: две разные семантики в двух разных контрактах.

Цена варианта B названа числом: 303.9 МиБ текста, 301.8 МиБ из них на двух типовых конфигурациях.
Времени такая стадия ещё не меряла — прогон V46 (BGU2, 44 с) текстовой стадии не включал, потому что
она не запрашивалась. Первый прогон П4 обязан назвать это время, а не пропустить его.

**Q3 (номер и имя проверки) — принят по умолчанию: узел V47, `tools/check_v47_configuration_object_modules.py`.**
Имя узла используется самим оператором в фиксациях с 28.10.2026 (`V47 Q1…`, `V47 Q2…`), возражение

**Q4 (форма входа) — решено оператором 28.10.2026: загрузка последовательна по дереву конфигурации,
группа объектов загружается полностью.**

Позиция оператора (смысл, названный им):

- конфигурация без модулей — такая же «битая» конфигурация, как и без свойств; работать с ней нет
  смысла, поэтому модули объектов не могут быть факультативной частью, отложенной на отдельную
  просьбу;
- разделять загрузку свойств объектов и загрузку их модулей — это риск ошибок и повторного чтения
  всей конфигурации;
- загрузка идёт последовательно, в соответствии с деревом конфигурации, и **если группа объектов
  загружена, она обязана быть загружена полностью**.

Что из этого следует для узла:

- **флага просьбы нет.** Модульная стадия выполняется в том же вызове `load_1c_catalog_tool`, всегда,
  после записи содержимого соответствующих объектов. Решение Q6 сохраняет границу транзакций
  (содержимое объектов — один коммит, их модули — следующий), но не право не читать код;
- **атомом полноты является группа объектов** (вид метаданных: `Catalogs`, `DocumentSchemas`,
  `AccountingRegisters`, …), а не вся конфигурация и не отдельный модуль. Записали группу — записали
  и её модули; незавершённая группа загруженной не называется. Это же становится границей проверки П5:
  полнота считается по группам, а не одним числом по конфигурации;
- отказ группы останавливает загрузку с текстом ошибки (правило C5 закрытого контракта и прежнее
  поведение конвейера), а ответ обязан назвать незакрытые группы прямо: «конфигурация неполная —
  группа X не загружена». Сказать «✅ загружено» без этой строки значило бы утверждать полную
  конфигурацию, которой нет;
- из прецедента V45/V46 берётся только половина: стадия в цепочке — да; отдельный инструмент — не как
  второй способ получить конфигурацию, а только как путь повторить отказанную стадию. Этот остаток
  требует отдельного ответа (Q4.1 ниже).

**Q4.1 (остаток Q4) — решено оператором 28.10.2026: отдельного инструмента нет, дозагрузки нет.**

Правило, названное оператором, одно: **ошибка загрузки влечёт перезагрузку всей конфигурации.**
Никакой частичной дозагрузки («только модули», «только группа») на текущем этапе не появляется.

Что из этого следует:

- `load_configuration_object_modules_tool` **не вводится**; реестр инструментов core остаётся
  **пяти** (`@mcp.tool()` в `server_configurations_core.py`, `EXPECTED_TOOLS` в
  `tools/check_mcp_tool_wiring.py` не меняется);
- предупреждение загрузки для модулей объектов **не обещает** «повторить стадию отдельно» — оно
  называет незакрытую группу и требует полной перезагрузки:
  `load_1c_catalog_tool(source_path=…, force=True)`. Прежние формулировки V44/V46, которые зовут
  повторить стадию отдельным инструментом, остаются как есть (это чужие узлы), но новой такой ссылки
  узел V47 не добавляет; расхождение двух правил в одном конвейере называется в карточке слоя,
  а не сглаживается;
- следует из этого и требование к порядку работы загрузчика: **дешёвые проверки раньше дорогих**.
  Раз отказ всё равно стоит перезагрузку всей конфигурации, путь модуля и его существование
  (`kind_unresolved`, `container_unmapped`, отсутствие файла) разрешаются до чтения кода — иначе
  отказ приходит после прочтения сотен мегабайт. Это инженерное следствие решения, а не новое
  решение оператора, и в карточках оно не появляется;
- снятие прежних строк круга узла перед записью обязано быть идемпотентным: повтор начинается со
  снятого, и вторая загрузка не должна оставлять удвоенных строк (мера — как в прогонах V46).

**Что записано.** `src/configuration_module_writer.py` — писатель строк узла в `bsl_modules`:

**Дефект самой пробы, найденный её же прогоном.** Проверка «`parent_uuid` разрешается записью
индекса» соединяла строку с индексом условием `o.uuid = parent_uuid AND o.child_type = module_type`,
то есть требовала от записи-владельца `child_type` слота. У владельца свой `child_type` (`Catalog`,
`Command`), поэтому проба отдала 79 «неразрешённых» строк на корректных данных, а соседняя проверка
`object_type`/`object_name` — пустое множество вместо ответа (число 0 без сопоставленных строк —
ответ пустой, и это тоже дефект проверки). Разрешение построено тем же способом, каким его строит
словарь: запись модуля ищется по `parent_name` + `child_type`, её родитель и есть `parent_uuid`;
добавлена отдельная проверка «число сопоставлений = число записанных строк», чтобы первая не могла
остаться пустой незаметной.

**Замер `_v47_p3_text_measure.py`: эталоны П6 переписаны на числа строк.** Писатель применён к

Причина различия — состояние выгрузки, а не дефект вывода: пустой модуль записывается файлом из

- эталоны П6 — 79 / 93 / 4 461 / 6 239 (всего 10 872), записей индекса без строки — 2 517, из них

- решение Q2 подтверждается числом: пустой модуль — 18 % записей круга, и строка «текста нет»
  раздула бы `bsl_modules` ровно на них (тот же аргумент, что у D6 узла V46).

**Что это даёт П4.** Точка входа модульной стадии — `write_object_modules(cur, configuration_uuid,
dump_root=… | dump_dir=…, changed_at=…, cache=…)`; курсор — курсор второй транзакции загрузки.
Вызывающий обязан: позвать `abandon_written_rows` при `status = "error"` и назвать `failed_group`
в ответе; передать один `changed_at` на всю загрузку; после успеха позвать `refresh_table_statistics`
(мера V46). Атомарность группы даёт транзакция, а не порядок вставки: страницы по 200 строк
проходят и в пробе (KomMag, E-контур), и по умолчанию — результат не меняется.
