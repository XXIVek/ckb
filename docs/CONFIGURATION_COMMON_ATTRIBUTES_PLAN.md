# Узел V50 (план): общие реквизиты (CommonAttributes) — позиция 2.5 нормативного списка, группа E модели A–H

План написан по итогам шага П0 (30.10.2026). Числа раздела 2 — результат прогонов
`_v50_p0_layout_probe.py`, `_v50_p0_probe.py`, `_v50_p0_index_probe.py` и вспомогательных
`_scratch/_v50_sep_blocks.py`, `_scratch/_v50_dump_cards.py`; повторный прогон обязан дать те же
значения (раздел 11.1). Ни одно решение раздела 3 ассистент не принимает сам.

## 1. Что есть и чего нет

Есть:

- заголовок конфигурации и индекс состава — узлы V32/V33; строки индекса вида `CommonAttribute.<Имя>`
  существуют во всех четырёх выгрузках, где вид есть (замер 2.9);
- **перечень общего вида в строке заголовка**: колонка `configurations.common_attributes TEXT[]`
  заполнена — MinCfg 2 значения, BGU2 7, BP3 7, KomMag NULL (замер `_v50_p0_index_probe.py`,
  раздел 2.9). Третья нога инварианта круга существует до начала узла — редкий случай, у ролей
  (V49) и параметров сеанса (V48) перечень тоже был, но для V50 он назван здесь, потому что
  именно он даёт независимую проверку круга;
- закрытые стадии конвейера: S1–S2 (заголовок, индексы), S3 (модули корня, V44), S4 (подсистемы и
  общие модули, V46), S4b (модули объектов, V47), S4c (параметры сеанса, V48), S4d (роли, V49);
- два прецедента формы хранения, на которые опирает раздел 4: `subsystems` + `subsystem_content`
  (V46 — перечень `<Content>` с `ordinal` и разрешением ссылки) и `session_parameters`
  (V48 — замкнутые словари блока `<Type>`);
- прецедент разрешения целей строкой-детём: `role_rights` (V49 — `target_kind`, `target_full_name`,
  `target_object_id`, `target_object_uuid`, `target_resolve_state`, `target_unresolved_path`).

Нет:

- таблиц вида — ни `common_attributes`, ни `common_attribute_targets` в живой схеме нет; запрос по
  `information_schema.tables` с масками `%common%`/`%attribute%` возвращает только `attributes`,
  `common_module_sources`, `common_modules` и витрины `v_current_*` к ним (замер 2.11);
- разбора `CommonAttributes/*.xml`, стадии, инструмента, постоянной проверки;
- в модели A–H (`docs/config-scenarios/01_configuration.md`, строка группы E) `CommonAttributes/`
  отнесён к «объектам без дочерней структуры — только свойства» с предложением колонки
  `configuration_objects.properties jsonb`. Замер этой формулировке противоречит: у каждого файла
  вида есть перечень `<Content>` — 1 512 строк на корпус (2.4), то есть дочерняя структура у вида
  всё-таки есть, просто она не файлами, а ссылками. Узлы V46 и V48 от этой формулировки уже
  отступили в пользу отдельных таблиц (решение D1); Q1 требует решить, повторяем ли отступление.

### 2.8 Имена и uuid между выгрузками: предопределённость измеряется, а не выдумывается

Различных имён по корпусу — 9. Из них **7 присутствуют и в BGU2, и в BP3 с идентичными uuid**:
`КомментарийЯзык1`, `КомментарийЯзык2`, `НаименованиеЯзык1`, `НаименованиеЯзык2`,
`ОбластьДанныхВспомогательныеДанные`, `ОбластьДанныхОсновныеДанные`,
`ОтредактированныеПредопределенныеРеквизиты`. Ещё два — тестовые имена MinCfg
(`ОбщийРеквизит1`, `ОбщийРеквизит2`) с собственными uuid.

Признака предопределённости в XML **нет** — ни флага, ни отдельного блока. Совпадение uuid между
конфигурациями — наблюдение, а не знание выгрузки (тот же порядок, что с отсутствующим признаком
у ролей, позиция O3 узла V49). Следствие для ключей: uuid общих реквизитов **общие для двух
конфигураций**, поэтому ключ строки обязан включать конфигурацию — Q2 (прецедент V47: без границы
по конфигурации ссылка включения BP3 упала на ключ BGU2 и уронила стадию S4).

## 3. Решения оператора — до кода (задавать по одному)

Ни одно решение не принято ассистентом самостоятельно: каждое меняет схему или контракт ответа, то
есть то, что правится потом перезагрузкой всех конфигураций. Формат: вопрос → варианты → что следует
из замера. Рекомендуемый вариант помечен «⟶ рекомендуется» и не считается принятым, пока не назван
оператором.

**Принято 30.10.2026.** Оператор подтвердил Q0 (номер узла и все имена: стадия
`s4e_common_attributes`, таблицы `common_attributes` + `common_attribute_targets`, модуль
`src/configuration_common_attributes.py`, инструмент `load_common_attributes_tool`, проверка
`tools/check_v50_common_attributes.py`) и указал приступить к реализации, то есть принять
рекомендованные варианты Q1…Q10 (вариант A везде). Два отступления от эскиза раздела 4, которые
обязаны быть названы здесь, а не в комментариях постфактум:

- **Q2, форма ключа применения.** Эскиз предлагал `UNIQUE (configuration_uuid,
  attribute_object_uuid, revision_no, ordinal)` (форма `subsystem_content` V46). Принята форма
  `UNIQUE (common_attribute_id, ordinal)` (форма `role_rights` V49): uuid общих реквизитов общие
  для конфигураций (2.8), поэтому uuid в ключ не кладётся вовсе, а граница конфигурации и
  конкретной ревизии держится ссылкой на строку родителя. Замер 2.4 (повторов цели внутри
  реквизита — 0) делает `ordinal` достаточным различающим столбцом и одновременно хранит порядок
  перечня.
- **Раздел 4, CHECK по значениям словарей платформы.** Эскиз обещал «колоночные ограничения на
  каждый замкнутый словарь». Принято решение НЕ класть CHECK по значениям свойств: словарь замкнут
  замером по четырём выгрузкам, XSD вида в слое схемы нет, и CHECK означал бы отказ записать
  конфигурацию из-за значения платформы, которого мы не ждали (прецедент Q4 узла V49). Вместо
  этого — состояние строки `properties_state` ('all_known' / 'unknown_value' / 'unknown_tag') с
  перечнем виновников `unknown_property_names`; норматив словарей держат константа разбора и

  (`type_multiplicity`, `type_parse_state`, `use_state`, `*_resolve_state`, `content_state`,
  `properties_state`, пары «изменение/признак»).


**Q0. Номер узла и имена.** V50 — следующий после V49 (закрыт 30.10.2026). План, стадия

**Q1. Модель хранения: таблицы вида или общая колонка группы E.**
- *Вариант A.* `common_attributes` (строка реквизита) + `common_attribute_targets` (строка

  строк не является препятствием: 1 512 строк — это не 294 МБ текстов модулей (V46, решение D-S4).
- Риск A, который надо назвать вслух: имя таблицы `common_attributes` совпадёт с колонкой заголовка

**Q2. Ключ строки применения.**

⟶ рекомендуется: вариант A.

## 4. Модель схемы (по решениям Q1–Q7; не принята, пока ответы не названы)

Эскиз — чтобы объём правки был виден до ответов. Имена колонок соответствуют прецедентам
`roles`/`role_rights` (V49), `session_parameters` (V48), `subsystem_content` (V46).

**`common_attributes`** — строка реквизита: `configuration_uuid`, `object_uuid`, `object_name`,
`full_name`, `comment`, `synonym jsonb`, `tool_tip jsonb`, `source_path`; свойства формата и ввода
(`password_mode`, `format`, `edit_format`, `mark_negatives`, `mask`, `multi_line`, `extended_edit`,
`min_value`, `max_value`, `fill_from_filling_value`, `fill_value`),
свойства выбора (`fill_checking`, `choice_folders_and_items`, `choice_parameter_links`,
`choice_parameters`, `quick_choice`, `create_on_input`, `choice_form`, `link_by_type`,
`choice_history_on_input`, `auto_use`), свойства разделения (`data_separation`,
`separated_data_use`, `users_separation`, `authentication_separation`,
`configuration_extensions_separation`) и три ссылки-разделения по Q5, свойства обслуживания
(`indexing`, `full_text_search`, `data_history`); блок `<Type>` по Q6
(`type_raw`, `type_multiplicity`, `type_parse_state`, `types jsonb`, `type_qualifiers jsonb`);
счётчики `targets_count`, `targets_used_count`, `targets_not_used_count`; состояния
`content_state` (`with_content`, `empty_content`) и `properties_state` (`all_known`,
`unknown_value`, `unknown_tag`) с перечнем `unknown_property_names`; ограничения — на состояния,
выведенные самим слоем, и на согласованность счётчиков с состоянием (CHECK по значениям словарей
платформы не кладётся, см. «Принято 30.10.2026» в разделе 3); ключ
`UNIQUE (configuration_uuid, object_name, revision_no)`; колонки ревизий.

**`common_attribute_targets`** — строка применения: `common_attribute_id` (FK `ON DELETE CASCADE`),
`configuration_uuid`, `attribute_object_uuid`, `attribute_full_name`, `ordinal`, `target_kind`,
`target_full_name`, `target_object_id`, `target_object_uuid`, `target_resolve_state`,
`target_unresolved_path`, `use_state`, `conditional_separation_state` (всегда `empty_value` на
корпусе — граница, а не молчание); ключ `UNIQUE (common_attribute_id, ordinal)` — принятая форма
Q2 (см. раздел 3), отдельной колонки `target_ordinal` нет, порядок держит `ordinal`; индекс по
`target_full_name` и частичный по `target_object_uuid` — это и есть запрос «какие общие реквизиты
у этого объекта».

Витрина `v_current_common_attributes` и регистрация её в словаре версионных
(`CONFIGURATION_VERSIONED_TABLES`); `common_attribute_targets` — безцепочечная таблица, попадает в
`CONFIGURATION_UNVERSIONED_TABLES` по прецеденту `role_rights`, а её витрина
`v_current_common_attribute_targets` строится связкой.

Состояний файлового круга (`index_only`, `file_only`, `uuid_mismatch`, `directory_missing`) в
таблице нет осознанно — по прецеденту V48 их называет ответ стадии и постоянная проверка узла
(Q8, Q9), а не строка: строка вида пишется по файлу, подтверждённому индексом состава, и
отсутствие каталога — свойство выгрузки, а не реквизита.

Признака предопределённости в эскизе нет (Q7): ни колонки, ни производного флага. Единственное
выраженное в схеме наблюдение о совпадении uuid между конфигурациями — сам ключ с
`configuration_uuid` (Q2), который такое совпадение не путает.

## 5. Контракт стадии и ответа

Стадия `s4e_common_attributes` идёт в `STAGES` после `s4d_roles` и перед `s4b_object_modules`
(порядок повторяет нормативный список, 2.12). Ключ ответа — тот же, что у соседних стадий:
`source_path` каталога выгрузки либо `configuration_uuid` заголовка; расхождение uuid называется
отказом, а не разрешается молча (прецедент V44/V46/V48/V49).

Разделы ответа:

- **СОСТАВ** — число файлов каталога, число строк индекса, число значений перечня заголовка,
  множество расхождений между ними; при отсутствии каталога — `files_found = 0` и наблюдение
  `directory_missing` (Q9);
- **СВОЙСТВА** — число записанных строк, состояния свойств, состояния разбора `<Type>`
  (`parsed` / `partial` / `absent` / `unknown_form`), число строк с неизвестным значением словарного
  свойства (`unknown_value` — на корпусе таких 0, но граница обязана называться);
- **ПРИМЕНЕНИЕ** — число строк, разбивка по `use_state`, разбивка по видам целей, результат
  разрешения (`exact` / `prefix_only` / `unresolved`);
- **РАЗДЕЛЕНИЕ** — число непустых ссылок по каждому блоку и результат их разрешения;
- **СНЯТО** — какие строки прежней загрузки сняты при повторной загрузке (история состояний не
  заводится, прецедент D8);
- **СТАТИСТИКА** — `ANALYZE` по записанным таблицам; отказ — предупреждение, а не отказ загрузки
  (прецедент V46: без статистики счётчик витрины считается минутами).

Отказ разбора **любого** файла круга останавливает стадию до записи: половина круга в базе читалась
бы как полный состав вида (приём V48).
