# Промт-проверка: работа системы правил (узел RULE-LAYER / RULE-V2)

Документ — инструмент проверки, а не норматив: он нужен, чтобы в свежном контекстном окне
проверить, что система правил (маршрутизатор → индекс слоя → карточка) работает, и отделить
знание, которое ассистент нашёл, от знания, которое ему подсказали.

Граница честности: текст `§1` вставляют в новое окно как есть. В нём нет ни одного адреса
карточки, ни одного имени скрипта и ни одного числа — иначе проверка проверяла бы подсказку,
а не поиск. Контрольные точки (`§2`, `§3`) читает только оператор, в контекст они не попадают.

Состояние на момент написания: 24.10.2026, после коммитов `c2872bb1` (RULE-LAYER v2) и
`bfc4bd03` (снимки слоя вынесены из ссылок правил в .gitignore).

## §1. Промт (вставить в новое окно, режим — чтение)

```text
Задача — ответить, как в этом проекте устроена работа с правилами MCP-серверов, по фактическому
состоянию, а не по памяти. Режим — чтение и диагностика: файлы не правь.

Порядок, который обязан соблюдаться (он и есть предмет проверки):
1. Начни с Шага 0 поиска по документации, дальше иди по маршрутизатору правил: индекс слоя →
   карточки слоя. Чтение двухфазное: выдача поиска даёт id и превью, содержимое читается
   отдельным инструментом по id.
2. Ответ строй по адресам карточек (заголовкам строк слоя), а не по файлам правил целиком.
   Категория при поиске обязательна.
3. Не утверждай о том, чего не читал. Имена скриптов, файлов, колонок и констант подтверждай
   чтением кода или карточки; если чего-то нет — скажи прямо.
4. Числа проверок бери только из прогона, который запустил сам, и называй команду прогона.
5. Расхождение текста правила с кодом назови, но не исправляй: предложи правку списком.

Вопросы (по порядку):
1. Как правильно исправить правило слоя и чем доказывается, что правка не сломала слой?
   Назови цикл целиком: где исходник, чем он переносится в строки базы, чем проверяется.
   Почему правка только строк базы — не рабочий путь?
2. Какие состояния карточек правил существуют и чем различаются по требованиям? Почему
   «снимок прежних правил» и «заявленное, но не сформулированное правило» — разные состояния,
   если оба не являются действующим правилом?
3. Чем доказывается, что тексты правил совпадают с кодом? Запусти эту проверку и назови её
   итог. Найди и назови расхождения, если они есть.
4. Что требуется, чтобы завести новый слой правил (например, для ещё одного MCP-сервера)?
   Перечисли места, где обязаны появиться записи, и что отвалится, если пропустить одно.
5. Что из артефактов слоя намеренно не хранится в репозитории и чем вместо этого проверяется
   целостность слоя?
6. Что делать, если правка меняет адреса карточек (переименование состояний)? Какая часть
   ссылок при этом рассинхронизируется и чем это лечится?

Отдельным блоком в конце — журнал действий:
- какие инструменты вызывал и с какими аргументами (первым — что именно);
- какие адреса разрешились, какие id читались полностью, какие — только превью;
- что не нашлось или разрешилось не тем, чем ожидалось;
- какие команды проверок запускал и какие числа получил.
```

## §3. Как фиксировать результат

После прогона в новом окне оператор отмечает три числа (в ответе ассистента их быть не должно —
это вывод наблюдения):

1. сколько обращений к слою было сделано до первого ответа по существу (норма: индекс + 2–4
   карточки, не 10);
2. сколько утверждений подтверждено адресом карточки или чтением кода (норма: все имена
   скриптов, констант и файлов);
3. сколько красных флагов из списка выше появилось (норма: 0).

Провалом считается и случай, когда ассистент ответил верно, но ни разу не назвал адрес
карточки: верный ответ без адреса означает, что знание пришло не из слоя, а из текста
маршрутизатора или из памяти модели, — то есть система правил не работала.
