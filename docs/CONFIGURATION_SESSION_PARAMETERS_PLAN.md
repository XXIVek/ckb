### 2.10 Ограничения схемы: что выражается именованным отказом (прогон шага П1, 29.10.2026)

| случай | чем ответил корпус | что это значит для модели |
|---|---|---|
| две записи `types`, заявлен `single` | `violates check constraint "session_parameters_type_multiplicity_matches_types"` | кратность выражается схемой (Q4) |
| `absent` при непустом массиве | тот же отказ | противоречие видно по числу записей |

| `types` — объект, а не массив | `violates check constraint "session_parameters_types_is_array"` | форма верхнего уровня выражается |
| лишние ключи записи и дубликат `value` во второй записи | строка **принята** | граница выражимости: это сторожит проверка Q6, а не схема (замер 2.5) |
| `changed_at` без `changed_by`; `revision_no = 0` | именованные отказы пары и номера ревизии | пары V46/V47 повторены |
| `types @> '[{"target_full_name":"Catalog.Организации"}]'` по витрине | 1 строка | содержательный запрос идёт по витрине, GIN заведён под него |
| вторая ревизия по тому же `object_name` | витрина отдаёт 1 строку, `revision_no = 2`; тот же `object_name` в другой конфигурации — отдельная строка | ключ Q2 с границей `configuration_uuid` работает, правило A1 не сломано |

Дефект первой формулировки CHECK, который прогон вскрыл и исправил тем же шагом: плоский
`CHECK (type_multiplicity = case when jsonb_array_length(types) = 1 …)` для НЕ-массива отвечал
внутренним текстом `cannot get array length of a non-array` вместо отказа
`session_parameters_types_is_array` — граница формы верхнего уровня переставала быть
именованным отказом. Итоговая формулировка ставит проверку формы первой веткой `CASE` (порядок
веток `CASE` гарантирован, в отличие от плоского `OR`, где порядок подвыражений не
оговаривается). Отдельная граница, названная прогоном: голое константное выражение
(`SELECT jsonb_array_length('5'::jsonb)`) планировщик вычисляет до исполнения, поэтому
ограничение снимается по значению колонки (вставка через `SELECT … FROM (VALUES …)`), а не по
литералу — оба варианта в зонде есть, оба дают именованный отказ.

## 3. Решения оператора — до кода (задавать по одному)

Ни одно решение не принято ассистентом самостоятельно: каждое меняет схему или контракт ответа, то
есть то, что правится потом через перезагрузку всех конфигураций. Формат: вопрос → варианты → что
следует из замера. Рекомендуемый вариант назван явно и помечен «⟶ рекомендуется»; он не считается
принятым, пока не назван оператором.

**Q0. Номер узла.** V48 — следующий после V47 (V47 закрыт 28.10.2026). План, зонды и ветка журнала
называются по этому номеру, проверка — `tools/check_v48_session_parameters.py`.
⟶ рекомендуется: подтвердить V48. **Принято оператором 29.10.2026: V48.**

**Q1. Модель хранения: отдельная таблица или `properties jsonb`.**

Ограничения (перечислены, потому что молчаливое отсутствие CHECK — это отсутствие договорённости):

- `session_parameters_configuration_object_revision_key` — `unique (configuration_uuid, object_name,
  revision_no)` (Q2, вариант A);
- `session_parameters_type_multiplicity_known` — CHECK по закрытому словарю `absent | single |
  composite` (определение оператора, Q4);
- `session_parameters_type_multiplicity_matches_types` — CHECK
  `case when jsonb_typeof(types) <> 'array' then true else type_multiplicity = case when
  jsonb_array_length(types) = 1 then 'single' when jsonb_array_length(types) > 1 then
  'composite' else 'absent' end end`. Ограничение выражимо — в отличие от формы отдельной
  записи: БД принимает такой CHECK и отклоняет им строку «две записи, но `single`» (замер
  `_v48_q4_jsonb_probe.py`, текст отказа `violates check constraint "c_multiplicity"`).
  Проверка формы в первой ветке `CASE` — не косметика: без неё та же формула для НЕ-массива давала
  внутренний текст `cannot get array length of a non-array` вместо именованного отказа
  `session_parameters_types_is_array` (замер 2.10, прогон П1 29.10.2026);
- `session_parameters_types_is_array` — CHECK `jsonb_typeof(types) = 'array'` (форма верхнего уровня
  выражается, форма записи — нет);
- `session_parameters_types_absent_matches_no_block` — CHECK
  `(types = '[]'::jsonb) = (type_multiplicity = 'absent')` и
  `type_parse_state = 'absent' ⇔ type_multiplicity = 'absent'`: «не разобрали» не равно «типа не
  было» (Q3, вариант A);
- `session_parameters_type_parse_state_known` — CHECK по закрытому словарю состояний разбора;
  словарь задаёт разбор, а схема повторяет его минимально (прецедент V46: словарь
  `declaration_state` CHECK не получил, чтобы не разъезжаться с кодом);
- **что CHECK не выражает и кладётся в постоянную проверку Q6** (замер 2.5: БД отклоняет такие
  ограничения текстом `cannot use subquery in check constraint`): обязательные ключи каждой записи
  (`value`, `class`, `state`); согласованность `class` и ключей цели; отсутствие двух записей с
  одним `value` у параметра; равенство числа записей числу `<v8:Type>` в файле. Уникальный индекс по
  элементу jsonb возможен только по первой записи (`(types -> 0 ->> 'value')`), поэтому дубликат
  второй записи проходит как обычная вставка — это и сторожит проверка, а не схема;
- пара-проверки в духе V46/V47: `revision_no >= 1`, `changed_by IN ('load','edit','restore')`,
  пара `changed_at ↔ changed_by`.

Индексы: уникальный ключ цепочки; `idx_session_parameters_configuration_uuid` (обслуживает витрину и
чистку узла); `idx_session_parameters_object_uuid_revision` по образцу
`idx_subsystems_object_uuid_revision` (поиск по uuid метаданных — колонкой ключа он не становится,
Q2); GIN `idx_session_parameters_types_gin USING gin (types jsonb_path_ops)` — именно он отвечает на
содержательный вопрос вида «какие параметры сеанса указывают на справочник Организации» через
containment `types @> '[{"target_full_name":"Catalog.Организации"}]'` (замер 2.5: план с
Bitmap Index Scan по GIN при выключенном последовательном скане). Частичный индекс
`WHERE type_multiplicity = 'composite'` создать можно (замер подтверждён), но он не заводится:
составных типов 6 файлов из 207 (2.4.3) — это фильтр вывода, а не путь поиска, и индекс под фильтр
в таблице такого размера только расходует место.

Витрина `v_current_session_parameters` — по образцу `v_current_subsystems` /
`v_current_common_modules`: колонки перечислены явно, строка относится к ревизии, признанной
текущей. Имя витрины даёт `current_view()`; словарь `CURRENT_VIEWS` порождается из
`VERSIONED_TABLES`, поэтому регистрация узла — одна запись в
`CONFIGURATION_VERSIONED_TABLES` (`src/current_revision.py:98`), а не пять правок по коду. Витрина
перечисляет `types` и `type_multiplicity` своими колонками: содержательный запрос «какие параметры
сеанса указывают на объект» идёт по витрине, а не по таблице, и containment `@>` по jsonb работает на
витрине так же, как на таблице (замер 2.5).

Порядок правки DDL не меняется, но слой правки определяет, какой шаг правится: таблица
принадлежит слою конфигурации (шаг 2 установки — `create_1c_configurations_db.sql`), а не слою
внешнего объекта, поэтому генератор `src/generate_ddl.py` (шаги 1 и 1b —
`src/ddl_external_report.sql`, `src/ddl_enrichment.sql`) этим узлом **не трогается** и
перегенерация порождённых файлов не нужна. Правка идёт парой «шаг 2 + аддитивная
`migrate_v48_session_parameters.sql`»; порождённые файлы руками не правятся.

## 5. Контракт стадии и ответа

Стадия (Q5, ответ оператора 29.10.2026 — своя, а не третий вид S4): в `STAGES` добавляется
`s4c_session_parameters` (`STAGE_SESSION_PARAMETERS`) — между `s4_child_objects` и
`s4b_object_modules`, потому что порядок стадий повторяет порядок нормативного списка (2.9: позиция
2.3 идёт сразу за 2.1–2.2); существующие стадии не
перенумеровываются и не меняют поведения **в части своего содержимого**; поведение конвейера при
отказе меняется для всех стадий решением Q8 (вариант A) и описано ниже, в подразделе «Остановка
конвейера». `CHILD_KINDS`, `CHILD_TABLES` и форматёр V46 этим узлом **не трогаются**. У стадии свой
ключ ответа — `session_parameters_defaults()`
и свой форматёр: правило C3 («ответ каждой стадии вложен в свой ключ») при отдельной стадии требует
своего ключа, а не разбивки по видам внутри чужого. Отказ стадии описывается тем же замкнутым
словарём, что и успех: `status` + `error` (прецедент `_stage_failure` V46/V47), вызывающий отличает
«стадия не выполнялась» от «слой отказал».

Что обязан назвать ответ стадии отдельно (иерархии состояний здесь нет, но классы расхождений те же):

- `counts_by_state` по типу: `parsed` / `partial` / `unknown_form` / `absent` — «тип не разобран»
  читается фактом, а не нулём;
- `types_unresolved` — число записей `types` с `resolved = false` и примеры (на четырёх выгрузках 0;
  ненулевое значение — это данные или новое правило перехода, а не молчаливый NULL);
- `types_multiplicity` — распределение `single` / `composite` / `absent` (по корпусу 201 / 6 / 0,
  2.4.3): кратность называется в ответе, потому что это свойство модели 1С, а не исключение данных;
- `index_only` / `file_only` — записей индекса без файла и файлов без индекса (замер 2.2 даёт нули,
  нули обязаны быть названы, а не подразумеваны);
- предупреждение о свойстве вне словаря (ровно приём V43 про «виды без колонки» и V46 про имена вне
  словаря): молча пропущенное свойство отличалось бы от «такого свойства в выгрузке нет».

`CHILD_NOT_IMPLEMENTED` — текст, который сейчас перечисляет незакрытые группы модели, — теряет из
списка параметры сеанса; меняется он тем же шагом, что и код, иначе карточка слоя будет обещать то,
чего уже нет. Сам круг `CHILD_*` при этом не расширяется: параметры сеанса закрывает отдельная
стадия, и в карточке слоя они больше не числятся среди видов `load_configuration_object_properties_tool`.

### Остановка конвейера по первой ошибке (Q8, вариант A)

Норматив: отказ любой стадии останавливает конвейер. Что меняется в контракте ответа конвейера
(`src/configuration_loader.py`), по пунктам принятого ответа:

| ключ ответа | что он значит после Q8 |
|---|---|
| `success` | `false`, если стадия отказала; раньше — всегда `true` после записи заголовка (замер: строка 855 `src/configuration_loader.py`) |
| `stopped_stage` (новый) | адрес остановленной стадии (`STAGES`), её `error`/`reason` и чем продолжить загрузку: отдельным входом (`load_configuration_root_modules_tool`, `load_configuration_object_properties_tool`, `load_session_parameters_tool`) или полной перезагрузкой (для `s4b_object_modules` отдельного входа нет — прецедент Q4.1) |
| `stages[].status` | отказавшая — `error`; стоящие после неё — `not_run` (правило C2: «не выполнялась» ≠ нули). Механизм в контракте есть: `STATUS_NOT_RUN` возвращают `*_defaults()` по умолчанию, форматёры печатают «Стадия не выполнена» для `not_run` и «Стадия не удалась» для `error` (`configuration_load_contract.py:367,537`) |
| `load_incomplete`, `incomplete_groups` | проставляются и при остановке: строки заголовка и индекса в базе остались, состав детей неполон |
| `warnings` | остаются, но перестают быть единственным признаком отказа: предупреждение без `success: false` больше не описывает отказ стадии |

Чего остановка НЕ делает (это прямо в ответе оператора): не откатывает заголовок, индекс состава и
перечни вида — стадии S3+ идут после коммита транзакции заголовка. Поэтому `success: false` обязан
сопровождаться строкой «заголовок и индекс состава записаны, состав детей неполон»: без неё `false`
прочитается как «в базе ничего нет», а это было бы неправдой.

Порядок стадий = порядок нормативного списка (2.9): `s4_child_objects` (2.1–2.2) →
`s4c_session_parameters` (2.3) → `s4b_object_modules`. Текущий порядок `STAGES` (S3 → S4 → S4b)
этому соответствует, потому что модули объектов отдельной позицией второго слоя в списке не стоят;
вставка `s4c` выполняется между S4 и S4b. Остановка имеет смысл только при совпадении порядка:
иначе она пропускает группы, стоящие раньше ошибки.

Дефект контрактного модуля, который этот шаг обязан назвать (замер 29.10.2026, чтение
`src/configuration_load_contract.py`): функция `child_objects_defaults()` определена в модуле **дважды**
— строки 181–182 (четыре ключа, прежний облик V45) и строки 323–345 (полный закрытый контракт V46).
Второе определение перекрывает первое, поэтому мёртвый код безвреден для работающего кода, но именно
эта функция возвращает `not_run` — тот самый статус, на котором стоит остановка. Оставлять в модуле
контракта два определения функции, задающей состояние стадии, значит оставить два разных облика
«стадия не выполнялась». Удаление мёртвого определения — часть шага П8, а не отдельный узел: оно
ничего не меняет в поведении и проверяется отсутствием второго определения.
