## 2. Три условия, которые обязаны быть выполнены до первой правки

1. **Снимок «до» обязателен вручную и после V19.** Каталоги выгрузки лежат вне git

   сохраняется текст карточки объекта с разбором макета — откатиться на прежнее состояние
   строками БД нечем.
2. **Ручное обогащение снимается вместе со строкой объекта.** `force=True` вызывает
   `delete_external_object()`, а он снимает и `config_aliases (origin='manual')`, и
   `config_snippets (is_verified=true)`, и `config_cross_references` (каскада по ним нет).

   инструментарий узла V35: `tools/export_manual_enrichment.py` (снимок в
   `snapshots/manual_enrichment/`) до перезагрузки и `tools/apply_manual_enrichment.py --apply`
   после перегенерации; порядок
   «сначала валидаторы, потом ручные строки» сохраняется всегда.
3. **Сегодня единственный способ сказать «что изменилось» — сравнение карточек и счётчиков**
   (`dcs_*`, `counts`, разделы `check_external_report_inventory.sql`). Механизм сравнения
   состояний в схеме с 18.10.2026 есть (цепочка ревизий + `children_manifest`, снимок имени
   не нужен), но заполняет его только загрузчик каталога, а инструмент правки, который писал бы
   `changed_by='edit'`, не реализован. Отдельная дыра замера 18.10.2026 закрыта тем же днём:

   `load_1c_catalog_tool(..., force=True)` — манифесты записаны (`Test1_Otchet` — 9 членов,
   `Test2_Otchet` — 3), сравнение состава детей по манифесту работает, карточка отдаёт строгий

| `origin_path` | путь-источник: каталог выгрузки либо файл `.erf`/`.epf` (для двоичного — сам файл, не каталог разбора); CHECK `external_report_origin_pair_check` держит пару с `origin_kind` | то же |
| `origin_sha256` | `sha256`: канонический digest поимённого listing каталога либо байты двоичного файла; CHECK `external_report_origin_sha256_check` (`^[0-9a-f]{64}$`) | то же |
| `origin_manifest` | состав входа (jsonb: `{kind, scope, …}`, для каталога — `files[]` и признак `truncated`) | то же |
| `origin_recorded_at` | момент фиксации провенанса | схема |

Индекс — `idx_external_report_origin_sha256` (btree по `origin_sha256`), обратный поиск «какие строки
загружены из этого файла/каталога».

Границы модели — ровно те, что нужны практике правки, и ничего сверх:

1. **Заполняет загрузчик, а не оператор.** `load_catalog`/`register_external_report` принимают
   `origin`/`origin_kind` (путь и вид входа), дальше `external_provenance.resolve_origin` → `collect`
   → `columns_of` → `compare` (`src/external_provenance.py`). `ibcmd_bridge` заявляет
   `origin_kind=ORIGIN_BINARY_FILE`. Заявлять провенанс вручную — значит получить строку, которая
   описывает не тот вход, которым её получили;
2. **`force=True` заново вычисляет и перезаписывает провенанс**, в отличие от `configuration_id`,
   который переносится (правило R11): строка описывает текущее содержимое, поэтому актуален источник
   текущего;
3. **отказ вычислить отпечаток — предупреждение, а не отказ загрузки** (пустой путь, файл недоступен,
   каталог разбора удалён): `collect` возвращает `success=False`, `columns_of` отдаёт пустые колонки,
   состояние читается как `not_recorded`. Отказ загрузки тут означал бы, что провенанс важнее объекта;
4. **`authored_layout` — резерв** за нашим собранным layout (узлы V29/V18), текущий загрузчик его не
   проставляет;
5. **провенанс есть только у `external_report`.** У `configurations` и `configuration_objects` колонок
   `origin_*` нет (решение D-C): заголовок конфигурации — единственная строка на `name`, индекс
   состава — производные данные, пересоздаваемые при каждой загрузке;
6. **провенанс — не версия.** Он отвечает на вопрос «откуда строка», а не «что в ней изменилось с
   прошлый раз»; история состояний — узел V19, реализованный 18.10.2026 частично (схема, манифест
   и витрины есть, инструмента правки нет — раздел 8). Поэтому снимок «до» из раздела 2 никуда не
   делся: отпечаток текущего входа не заменяет карточку состояния.

Чем проверять перед правкой: `SELECT origin_kind, origin_path, left(origin_sha256, 12),
origin_recorded_at FROM v_current_external_report WHERE uuid = '…'` — только в SQL-сверках
валидаторов (прямой SQL ответу оператору не служит, п. 5 правил core); читается витрина
текущего состояния, а не `external_report` — с V19 в таблице несколько ревизий на `uuid`
(правило S5). Живой контракт — `python tools/check_v31_provenance.py`.
