# Узел V51 (план): свойства планов обмена (позиция 2.6) и механизм дочерних объектов конфигурации

Дата плана: 31.10.2026. Продолжение ряда узлов нормативного перечня
`C:\1C_LLM\Структура конфигурации.txt` (2.1 V46 → 2.3 V48 → 2.4 V49 → 2.5 V50 → **2.6 Планы обмена**).
Номер узла V51 свободен: поиск `V51` по `docs/`, `src/`, `tools/` даёт ноль совпадений.

Отличия от V48/V49/V50 два, и оба меняют объём работы:

1. у вида **есть дочерние объекты** (реквизиты, табличные части, формы, макеты, команды) —
   узел закрывает не только «свойства вида» (группа E модели A–H узла V38), но и механизм
   детей (группы A/B/D), который дальше переиспользуется для других видов с детьми;
2. дети уже куда-то ложатся: таблицы `attributes`, `tabular_sections`, `forms`, `form_ext`,
   `templates` существуют с узлов V13/V19 и принадлежат внешним объектам. Значит узел не
   «создаёт таблицы», а **расширяет существующие** на объект конфигурации — это миграция
   ключей и витрин, а не новый слой с нуля.

| `Template` | 35 | 70 | 66 из 132 — ровно половина |

| `Content` / `Help` / `AdditionalIndexes` / модули | лежат файлами | есть | **uuid нет ни у одной строки** |

Три следствия, каждое из которых становится правилом проверки узла, а не «шумом»:

- **Форма и макет дают в индексе по две строки**: одна с uuid (сам объект), вторая без uuid
  (её содержимое `Ext/`). Инвариант круга обязан различать эти строки, иначе «лишние» строки
  индекса будут читаться как расхождение.
- **Стандартные реквизиты в индекс не попадают**: они не адресуемые объекты метаданных. В XML
  они есть (153 в BGU2, адресуются точечно — `…StandardAttribute.Code`), поэтому их надо
  называть отдельным состоянием, а не терять молча или смешивать с `Attribute`.
- **uuid детей в XML нет.** В файле вида есть атрибут `uuid` у самого вида, у детей —
  `xr:TypeId`, `xr:ValueId` и точечные `<xr:Field>`. Идентификаторы детей даёт индекс состава.
  Значит перечни uuid строятся из индекса, а не из XML — тот же приём, что у V43
  (48 колонок-перечней собираются из `ConfigDumpInfo.xml`).

### 3.2 Почему связь детей обязана включать конфигурацию (решающий замер)

```sql
SELECT count(*) FROM (SELECT uuid FROM configuration_objects
                      WHERE uuid IS NOT NULL GROUP BY uuid
                      HAVING count(DISTINCT configuration_id) > 1) t;   -- 42 349
-- среди детей планов обмена таких uuid — 14
```

Один uuid встречается в двух и более конфигурациях у **42 349** строк индекса. Связка
«uuid родителя + uuid ребёнка» без конфигурации уже сейчас сливает детей BGU2 и BP3.
Второй, независимый аргумент: витрина `v_current_attributes` разрешает текущую ревизию как
`NOT EXISTS (SELECT 1 FROM attributes h WHERE h.uuid = a.uuid AND h.revision_no > a.revision_no)`
— то есть **по uuid, без родителя и без конфигурации**. При переносе в эту же таблицу детей
объектов конфигурации она начнёт выбирать одну строку между двумя конфигурациями. Это не
гипотеза, а следствие определения существующей витрины.

## 5. Модель записи: что поставил оператор и что из неё следует

Постановка оператора от 31.10.2026 (принимается как основа модели):

- `Attribute` → таблица `attributes`, связь: uuid конфигурации → uuid родителя → uuid реквизита;
- `TabularSection` → `tabular_sections`, та же тройка;
- `Form` → `forms`, связь: uuid конфигурации → uuid родителя → **имя формы**;
- `Template` → `templates`, связь: uuid конфигурации → uuid родителя → **имя макета**;
- `Command` → новая таблица по образцу `attributes`, та же тройка;
- в таблице `exchange_plans` дети хранятся массивами: uuid или имена — по типу данных.

Из этого следуют четыре пункта, которые надо назвать до кода:

- **M1.** В `attributes` и `tabular_sections` нет ни `configuration_uuid`, ни `parent_type` —
  их вносит миграция; в `forms`/`templates` `parent_type` есть, но только со значением
  `external_report`, а `configuration_uuid` тоже отсутствует.
- **M2.** Действующий `UNIQUE (uuid, revision_no)` перестаёт быть достаточным: при одинаковых
  uuid детей в разных конфигурациях (замер 3.2) он не различает строки двух конфигураций.
- **M3.** Действующие витрины `v_current_*` надо перестроить на партицию с конфигурацией; для
  строк внешнего объекта конфигурация остаётся NULL — витрина обязана различать «конфигурации
  нет» и «значение не заявлено», а не склеивать их через `COALESCE`.
- **M4.** Идентификаторы детей берёт индекс состава (в XML их нет, п. 3), поэтому писатель детей
  работает в одной связке с разбором индекса, а не только с файлом вида. Порядок записи
  держится иерархией данных: строка вида → строки детей → перечни вида (по образцу V50: сначала
  строки с `RETURNING id`, затем зависимые — одной транзакцией).

### 5.1 Q1 закрыт: вариант A с двумя уточнениями оператора (31.10.2026)

Принято: **вариант A** (расширить существующие таблицы), с двумя поправками:

- **(а)** для `forms` и `templates` ключом служит **имя**, а не uuid ребёнка:
  `(configuration_uuid, parent_uuid, name, revision_no)`;
- **(б)** для внешних отчётов и обработок `configuration_uuid = parent_uuid` и равен uuid самого
  внешнего отчёта/обработки.

Семантика колонки после этого одна, и её надо писать в DDL-комментарии прямо:
`configuration_uuid` — **идентификатор области видимости родителя**: для объекта конфигурации это
uuid конфигурации, для внешнего объекта — uuid самого внешнего объекта. Внешнего ключа в схеме нет
осознанно (прецедент V20.1), поэтому ссылка не проверяется схемой, а проверяется загрузчиком и
проверкой узла.

Ключи после закрытия Q1:

| таблица | ключ текущего состояния | примечание |
|---|---|---|
| `attributes` | `(configuration_uuid, parent_uuid, uuid, revision_no)` | uuid ребёнка даёт индекс состава |
| `tabular_sections` | то же | |
| `commands` (новая) | то же | по образцу `attributes` |
| `forms` | `(configuration_uuid, parent_uuid, name, revision_no)` | имя уникально внутри объекта (`Forms/<Имя>.xml`); `uuid` остаётся обычным столбцом и используется для сопоставления с индексом (у строки-объекта формы он есть) |
| `templates` | `(configuration_uuid, parent_uuid, name, revision_no)` | то же (`Templates/<Имя>.xml`) |

Что закрытый Q1 меняет в существующих контрактах — и почему это безопасно (замеры 31.10.2026):

- **Витрины.** Все четыре устроены одинаково: `NOT EXISTS (SELECT 1 FROM <таблица> h WHERE
  h.uuid = a.uuid AND h.revision_no > a.revision_no)` — то есть разрешают текущую ревизию по
  uuid ребёнка, без родителя и без области видимости. После переноса детей конфигурационных
  объектов они начали бы выбирать одну строку между конфигурациями (замер 3.2: 42 349 общих uuid).
  При правиле (б) нога заполнена у всех строк, поэтому перестройка делается **без `COALESCE` и без
  ветвления на NULL**: партиция `PARTITION BY (configuration_uuid, uuid)` для таблиц с ключом по
  uuid и `PARTITION BY (configuration_uuid, parent_uuid, name)` для `forms`/`templates`.
  Прежние имена витрин сохраняются — они продолжают отдавать те же колонки.
- **Миграция данных выполнима целиком.** Сирот нет: 36 строк `attributes` из 36 и все строки
  `forms`/`templates`/`tabular_sections` имеют `parent_uuid`, равный uuid существующего внешнего
  объекта. Значит `UPDATE … SET configuration_uuid = parent_uuid` покрывает 36/3/2/2 строки, и
  колонку можно объявить `NOT NULL` без периода «значение не заявлено».
- **Правило (б) не теряет различие ревизий родителя.** В живой базе два внешних объекта, у каждого
  по одной ревизии (`external_report`: `revisions = 1`), то есть на текущих данных нога совпадает
  с `parent_uuid` без потерь. На будущее: узел V19 различает детей разных ревизий родителя не
  ключом, а манифестом родителя и собственной цепью `revision_no` ребёнка — правило (б) этот
  механизм не ослабляет, оно лишь добавляет ногу, которой не хватало (прежний
  `UNIQUE (uuid, revision_no)` был строже нового ключа только в одном смысле: он не различал
  одинаковые uuid детей в разных областях видимости, и именно это ломалось).
- **`form_ext`** ссылается на `forms(id)` FK с каскадом и дополнительно несёт
  `parent_uuid/parent_type` для витрины `v_current_form_ext`; её определение тоже построено по
  `forms.uuid`. Если содержимое форм останется за пределами узла (Q3), `form_ext` не трогается;
  если нет — в неё добавляется та же нога (это надо решить вместе с Q3).

### 5.3 Q3 и Q4 закрыты: цикл загрузки вида закрывается полностью (решение оператора, 31.10.2026)

Принцип оператора: загрузка обязана завершать цикл целиком, включая сохранение вторичных
объектов. Выбор варианта опирается не на принцип, а на замеры `_v51_p0_content_probe.py`:

| вторичный объект | MinCfg | BGU2 | BP3 | итого | куда пишется |
|---|---|---|---|---|---|
| содержимое форм `Ext/Form.xml` | 3 / 31.8 КБ | 34 / 456 КБ | 30 / 389 КБ | 67 / 877 КБ | `form_ext.ext` |
| бинарная форма `Ext/Form.bin` | 0 | 0 | **1 / 8.5 КБ** | 1 | `form_ext` (контракт V13/V14) |
| модули форм `Ext/Form/Module.bsl` | 2 / 11.9 КБ | 30 / 233 КБ | 23 / 137 КБ | 55 / 382 КБ | `form_ext.ext` по правилу **R9** (в `bsl_modules` модуль формы не дублируется) |
| макеты `Ext/Template.xml` / `.txt` | 0 / 1 | 9 / 26 | 9 / 21 | 18 + 48 / 33.2 МБ | `templates.ext` |
| слот `Ext/Content.xml` | 2 / 9 целей | 18 / **9638 целей** | 26 / **12 868 целей** | 46 / 22 515 строк | `exchange_plan_content` |
| слот `Ext/Help.xml` | 2 / 464 б | 8 / 1.9 КБ | 2 / 464 б | 12 / 2.8 КБ | исходный XML в `jsonb` (прецедент `subsystems.Content`, V46) |
| слот `Ext/AdditionalIndexes.xml` | 1 / 662 б | 0 | 0 | 1 | исходный XML в `jsonb`, состояние называется |

Почему выбран именно этот вариант, а не «дескрипторы без тел»:

- **разбор писать не нужно** — `src/external_subdir_parser.py` уже обходит `Forms/`, `Templates/`,
  `Ext/*.bsl` в терминах «каталог объекта», умеет бинарные формы (`Form.bin`) и извлечение модуля
  формы из контейнера; раскладка плана обмена для него — тот же layout, другой корень;
- **цена ограничена существующим контрактом**: `MAX_TEXT_CHARS = 1_000_000` символов с
  `ext_truncated` и обязательными `ext_size`/`ext_path`. По замеру усечение затронет несколько
  макетов-рекордсменов (4.2 / 10.4 / 18.6 МБ) — это называется состоянием, полный размер при этом
  известен всегда;
- **без содержимого карточка врёт о полноте**: `Content` отвечает на вопрос «что реплицирует план»
  (22 515 целей на три выгрузки), модули форм — 382 КБ BSL-кода, то есть ровно то, что нужно
  enrich-слою. Отдельный «узел содержимого» удвоил бы контракт состояний (цепь ревизий, витрины,
  инвариант `ext_size = octet_length(ext_bin)`) без выигрыша в информации.

Что при этом обязательно меняется в существующих контрактах:

- `form_ext` и `templates` получают **ту же ногу области видимости**, что и остальные таблицы детей:
  витрина `v_current_form_ext` построена связкой `JOIN forms f ON f.id = fe.form_id AND
  f.revision_no = fe.revision_no` плюс условие `NOT EXISTS (h.uuid = f.uuid …)` — без ноги она
  начнёт выбирать форму между конфигурациями;
- **модуль формы живёт в одном месте** — в `form_ext` (правило R9 слоя V14). В `bsl_modules`
  строк с путями `Forms/` сейчас 0, и узел их не добавляет; иначе один и тот же текст модуля
  лежал бы в двух таблицах с разными цепями ревизий;
- `exchange_plan_content` — самая большая таблица узла (22 515 строк на три выгрузки, максимум
  2587 целей у плана `ОбновлениеИнформационнойБазы` в BGU2). Строка: цель (`Metadata`), режим
  автозаписи (`AutoRecord`), порядок в файле, состояние разрешения цели
  (`exact`/`prefix_only`/`unresolved`) — по образцу `subsystem_content` (V46). Это вторая нога
  вопроса «что делает план обмена», поэтому она в этом узле, а не отложена.

## 7. План реализации (П1…П8)

**П1. Схемная пара и версионность.** Шаг в `create_1c_configurations_db.sql` + миграция
`migrate_v51_*.sql` + `src/ddl_configuration_tables.sql`:

- таблица `exchange_plans`: свойства вида, закрытые словари состояний,
  `revision_no`/`changed_at`/`changed_by`/`is_committed`,
  `UNIQUE (configuration_uuid, object_name, revision_no)` — по образцу `session_parameters` V48,
  потому что имя вида уникально в конфигурации, а uuid вида повторяется между конфигурациями;
  перечни детей по разделу 5.2;
- таблица `exchange_plan_content` (Q4: цель, `AutoRecord`, порядок в файле, состояние разрешения
  цели — по образцу `subsystem_content` V46; эталоны: 9638 целей BGU2, 12 868 BP3, 9 MinCfg),
  таблица `commands` по образцу `attributes`; слоты `Help`/`AdditionalIndexes` — исходный XML
  в `jsonb` по прецеденту `subsystems.Content` (V46);
- расширение четырёх таблиц детей (раздел 5.1): `configuration_uuid UUID NOT NULL`
  (+ `parent_type` в `attributes`/`tabular_sections`), предзаполнение
  `UPDATE … SET configuration_uuid = parent_uuid` (сирот нет — замер 5.1), снятие
  `UNIQUE (uuid, revision_no)`, новые уникальные ключи по таблице раздела 5.1;
- перестройка витрин `v_current_attributes`/`v_current_tabular_sections`/`v_current_forms`/
  `v_current_templates` на партицию с ногой области видимости (без `COALESCE`): имена и состав
  колонок сохраняются, меняется только разрешение текущей ревизии (замер 5.1: все они построены
  условием `NOT EXISTS (h.uuid = a.uuid AND h.revision_no > a.revision_no)`);
- **`form_ext` и `templates` получают ту же ногу** (Q3 закрыт в пользу полного цикла):

  `v_current_form_ext` связана с `forms` по `form_id`+`revision_no` и фильтрует по `forms.uuid`,
  поэтому без ноги она начнёт выбирать форму между конфигурациями; инвариант
  `ext_size = octet_length(ext_bin)` и пороги `MAX_TEXT_CHARS`/`ext_truncated` слоя V13
  сохраняются без изменений;
- параллельно — правка контуров правок внешних объектов (`check_v19`/`check_v20`/`check_v21`):
  они работают с `UNIQUE (uuid, revision_no)` и с витринами, и после смены ключа обязаны
  остаться зелёными без ослабления контракта `edit`/`restore`.

Словарь колонок — один источник (Python-модуль), как в V43/V46/V50.


**П2. Словарь свойств вида и словари состояний.** `EXCHANGE_PLAN_PROPERTIES` (замер раздела 2:
45–46 имён), `PROPERTY_VALUE_DICTIONARY`, словари состояний: свойства —
`all_known`/`unknown_value`/`unknown_tag`; дети — `with_children`/`empty_content`/
`indexed_no_file`/`file_not_in_index`; цель содержимого — `exact`/`prefix_only`/`unresolved`;
стандартные реквизиты — `present_not_indexed`/`absent`. Незнакомое значение свойства остаётся
значением с состоянием `unknown_value` и именем виновника (Q7 узла V50, вариант A), а не отказом.

**П3. Слой разбора `src/configuration_exchange_plans.py`.** Круг — файлы регистрации вида,
подтверждённые строками `configuration_objects` (с правилом пар форм/макетов из раздела 3), плюс
`configurations.exchange_plans` как независимая нога. Отказ разбора ЛЮБОГО файла круга
останавливает стадию ДО записи (приём V12/V46/V48/V49/V50); отсутствующий каталог вида — не
отказ, а `files_found = 0` с наблюдением `directory_missing` (KomMag даёт именно это).

Содержимое подкаталогов (`Forms/`, `Templates/`, `Ext/Content.xml`, `Ext/Help.xml`,
`Ext/AdditionalIndexes.xml`, `Commands/*/Ext/CommandModule.bsl`) разбирается
**переиспользованием `src/external_subdir_parser.py`**, а не новым обходом: слой уже понимает
раскладку «каталог объекта → Forms/<Имя>.xml → Ext/Form.xml | Ext/Form.bin → модуль формы»,
умеет бинарные формы (в BP3 они есть у планов обмена) и применяет пороги `MAX_TEXT_CHARS` с
признаком `ext_truncated`. Правило **R9** слоя V14 сохраняется: модуль формы пишется в `form_ext`,
в `bsl_modules` не дублируется (замер: строк с путями `Forms/` в `bsl_modules` сейчас 0).


**П4. Писатели.** Одна транзакция: строки вида (`RETURNING id`) → строки детей
(`attributes`/`tabular_sections`/`forms`/`templates`/`commands` с `configuration_uuid`,
`parent_uuid`, `parent_type='configuration_objects'`) → `form_ext` (описание формы + её содержимое
и модуль, правило R9) и содержимое `templates` → строки `exchange_plan_content` (22 515 строк на
три выгрузки — самая большая таблица узла, писать батчем) → слоты `Help`/`AdditionalIndexes` в
`jsonb` → перечни детей в строке вида. Снятие прежних строк вида — явный `DELETE` по
`configuration_uuid` (внешних ключей нет осознанно, прецедент V20.1); `form_ext` снимается
каскадом по `form_id` (FK сохранён). Время прогона не выдумывается: оно называется замером на П8
по аналогии с V50 (там весь круг общих реквизитов — 7 файлов и 817 строк — дал 1.22 с).


**П5. Инструмент `load_exchange_plans_tool`.** Отдельная точка входа на позицию перечня (решение
Q5 оператора узла V48): `source_path`, `configuration_uuid` (сверка uuid, расхождение — отказ),
`kinds` (Q5). Регистрация: `STAGES` в `src/configuration_load_contract.py`, `EXPECTED_TOOLS` в
`tools/check_mcp_tool_wiring.py`, раздел `===TOOLS===` матрицы `goal-and-stages`. Реестр станет
девять инструментов; сейчас расхождения нет (раздел содержит ровно восемь имён — сверено 31.10),
но автоматической сверки состава раздела с реестром по-прежнему нет: candidate-проверку разумно
делать на этом шаге, когда реестр реально меняется.

**П6. Проверка `tools/check_v51_exchange_plans.py`.** Инвариант круга по трём ногам: файлы
регистрации ↔ строки индекса (с правилом «форма/макет дают две строки: с uuid и без») ↔
`configurations.exchange_plans`; эталонные числа по четырём выгрузкам (MinCfg 2, KomMag 0 +
`directory_missing`, BGU2 18, BP3 — 26 объектов вида); счётчики детей с ожидаемыми словарями
состояний; отдельный тест-инвариант на замер 3.2: 14 общих uuid детей обязаны давать разные
строки в разных конфигурациях (это и есть защита от слияния).

Эталонные числа вторичного содержимого (замер `_v51_p0_content_probe.py`, они же — границы
полноты загрузки):

| что | MinCfg | BGU2 | BP3 |
|---|---|---|---|
| содержимое форм (`Form.xml`) | 3 | 34 | 30 |
| бинарные формы (`Form.bin`) | 0 | 0 | 1 |
| модули форм | 2 | 30 | 23 |
| макеты (`Template.xml` / `.txt`) | 0 / 1 | 9 / 26 | 9 / 21 |
| строки `Content` (целей) | 9 | 9638 | 12 868 |
| слоты `Help` / `AdditionalIndexes` | 2 / 1 | 8 / 0 | 2 / 0 |

Проверка обязана отличать «содержимое усечено (`ext_truncated`)» от «содержимого нет», и
«бинарная форма» — от «описания формы»: это три разных состояния, а не одно.


**П7. Нормативы и журнал.** Карточка `rules:core-rules:load-exchange-plans-tool`; матрица
`goal-and-stages` (строка стадии S4f, `===TOOLS===`, `===CHECK===`, дата матрицы);
`rules:core-rules:functional:load-catalog` (перечень стадий конвейера); снимок
`rules:core-rules:journal:node:v51`; прогоны `_layer_tree_check.py`, `check_rules_layer.py`,
`check_search_rules_sync.py`, `_journal_code_history.py`.

**П8. Прогоны остановки и повторной загрузки.** Вход вида в конвейер и выход только своего круга
(по образцу `_v49_p8_stop_probe.py`: порядок `STAGES`, пропущенные счётчики читаются из `STAGES`,
причина `full_reload_required`); идемпотентность повторного вызова (снятые строки названы);
одиночный вызов `load_exchange_plans_tool` без перезагрузки конфигурации. Известное ограничение
узла V50: прогоны по одной выгрузке нельзя запускать параллельно — они конкурируют за создание
заголовка конфигурации (наблюдение П8 V50, кодом не правится, называется в карточке узла).

## 8. Границы: чего узел V51 не закрывает

- группы A–H модели V38 для остальных видов: реквизиты и табличные части справочников,
  документов и прочего (механизм детей из этого узла для них переиспользуется, но круг каждого
  вида — отдельный узел), формы и макеты этих видов, предопределённые данные;
- тексты содержимого сверх порога `MAX_TEXT_CHARS = 1_000_000` символов: содержимое обрезается,
  ставится `ext_truncated`, полный размер называют `ext_size`/`ext_path` (контракт слоя V13) —
  усечение не является потерей данных, но и не выдаётся за полное содержимое;

- определённые типы (`DefinedTypes`, позиция 2.13): в выгрузке их каталога нет (замер 2.4.4,
  подтверждён узлом V50) — узла для них пока нет;
- реэкспорт (сборка изменённого объекта обратно в XML) — слой не реализован,
  `export_readiness_tool` отвечает честно;
- обогащение (алиасы/сниппеты) объектов конфигурации — enrich-слой работает с внешними
  объектами, цели вида — отдельный узел;
- предопределённость вида и его объектов (признака в выгрузке нет, позиция O3 узла V49);
- права, формы, макеты и команды других видов метаданных; `Help`/`AdditionalIndexes` как
  содержимое (в этом узле — только дескрипторы);
- позиция O1 узла V50 (формулировка смысла `DontUse` в карточке `load-common-attributes-tool`)
  остаётся открытой и этим узлом не закрывается.

## 9. Критерии готовности узла

1. все шаги П1…П8 имеют коммит, в плане нет символа незавершённости;
2. `tools/check_v51_exchange_plans.py` зелёная на четырёх выгрузках, включая KomMag как
   состояние `directory_missing`, и называет словари состояний, а не нули;
3. инвариант круга сходится по трём ногам с правилом пар форм/макетов; тест на 14 общих uuid
   детей проходит (строки разных конфигураций не сливаются);
4. регрессионный контур прежних узлов зелёный: `check_v50` (212/0), `check_v49` (373/0), `check_v48`
   (152/0), `check_v47` (119/0), `check_v46`, а также контур правок внешних объектов
   (`check_v19`/`check_v20`/`check_v21`) — он обязателен, потому что Q1 закрыт в варианте A и
   меняет их ключ и витрины;
5. миграция предзаполнила `configuration_uuid` значением `parent_uuid` у всех существующих строк
   детей (36/3/2/2), сирот после миграции ноль, колонка объявлена `NOT NULL`;
6. цикл загрузки закрыт полностью: у каждого загруженного вида есть строки детей, содержимое форм
   (`form_ext`, включая модули форм по правилу R9 и бинарную форму BP3), содержимое макетов,
   строки `exchange_plan_content` в эталонных числах таблицы П6 (9 / 9638 / 12 868 целей);
   пустое состояние названо словарём состояний, а не нулём;
7. `check_rules_layer.py`, `_layer_tree_check.py`, `check_search_rules_sync.py`,
   `_journal_code_history.py` — ноль ошибок; `===TOOLS===` матрицы содержит девять имён;
8. карточка журнала узла называет хеш закрытия и список коммитов (узел V50 показал, что
   объединение шагов в один коммит надо называть прямо, чтобы нумерация шагов не читалась как
   нумерация коммитов).
