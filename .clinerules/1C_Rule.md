# Инструкции для AI ассистента по программированию в 1С:Предприятие

## Роль

Я — AI ассистент по программированию в 1С:Предприятие.

## РАБОТА С ТЕРМИНАЛОМ

При работе с терминалом — запуск `psql.exe`, запросы к PostgreSQL, подключение к базам `local_doc` и
`ckb_1c_configurations` — читать карточку правил `rules:kb-rules:functional:db-access`: в ней строка
запуска с флагами, роли сервера (пользователь `postgres`, отсутствие роли `Buh`), какая база за что
отвечает и что делать с длинным выводом.

```powershell
python tools/rules_read.py "rules:kb-rules:functional:db-access"
```

Значение пароля держит файл `.env` в корне проекта (в репозиторий он не входит, шаблон —
`.env.example`); код и MCP-серверы читают его единственной точкой `src/db_env.py`.

Норматив живёт строкой базы `local_doc`, здесь остаётся только указатель: файл правил — маршрутизатор
(`rules:always:reading`), повторение правила в двух местах расходится молча.

## 📚 Правила работы с MCP-серверами — в базе `local_doc`

Правила четырёх MCP-серверов (`1c-knowledge-base`, `1c-configurations-core`,
`1c-configurations-enrichment`, `1c-configurations-export`) живут строками базы `local_doc`, а не в этом файле. Здесь остаются правила работы ассистента: роль, вывод, порядок обращения к правилам; нормативы подключения к базе — карточка `rules:kb-rules:functional:db-access`.

План по развитию самих правил контекста (что уже сделано, что дальше, чем мерить) —
`docs/RULES_CONTEXT_PLAN.md`. Это файл плана, а не правило: числа в нём — замеры на дату,
актуальные даёт прогон `python tools/check_rules_layer.py`.

### Чем читают правила

`python tools/rules_read.py` — инструмент чтения набора правил (узел RULE-READ). Поиском MCP
правила не читают: `search_docs_tool` отдаёт id, заголовок и превью в 200 символов, потому что
его алиасные и полнотекстовые шаги не гарантируют единственности ответа. Адрес карточки —
уникальный ключ, двумя адресами две карточки не описываются, поэтому правило чтения другое:

| запрос | что отдаёт |
|---|---|
| `--always` | полный текст того, что читается всегда (перечень ниже) |
| `--layers` | список слоёв: политика загрузки, назначение, число карточек, объём |
| `"rules:kb-rules:"` | родительскую карточку целиком, детей — списком адресов |
| `"rules:kb-rules:checks:index"` | одну карточку целиком, без усечения |
| `--tree <адрес>` | только перечень адресов поддерева, без содержимого |
| `find карант` | одна найденная карточка — целиком; несколько — таблица адресов |
| `--marked` | то же плюс строки, помечённые к удалению (узел Q1), с причиной |

Карточки, помечённые к удалению, по умолчанию не отдаются: скрытая строка не является правилом.
Инструмент только читает — правки делаются строками БД.

### Лог обращений к правилам

Каждое обращение к читателю правил дописывается в `logs/rules_load.log` (модуль
`tools/rules_logging.py`) краткой строкой: дата и адрес прочитанной карточки. По этим строкам
видно, когда и какое правило читали, и поднимался ли корень `rules:` — его адрес является такой же строкой. Подробный формат (режим вызова, id, объём, промахи, итог обращения) включается флагом `--full-log`: замеры делаются им, потому что краткая строка объёма не содержит.
Разбирает лог тот же модуль: `--tail`, `--stats` (частота обращений к заголовкам), `--check`
(целость сессий подробного формата и читаемость строк краткого), `--rotate` (перенос в
`logs/archive/`). Без записи в лог — `--no-log`, замер на отдельном файле — флаг `--log-file`.
Лог в репозиторий не входит (`logs/` в `.gitignore`): это наблюдение за прогонами, а не правило
и не доказательство замера.

### Если при выполнении задачи не хватает функциональности MCP

Сначала проверяют функции того MCP, с которым идёт работа, — поиск всегда с указанием сервера:

```powershell
python tools/rules_functions.py 1c-knowledge-base          # функции сервера: адрес + ===WHEN===
python tools/rules_functions.py kb-rules --term карантин    # есть ли функция под задачу
```

1. Функция найдена — её правило читают целиком адресом: `python tools/rules_read.py "<адрес>"`.
2. Функции под задачу нет — это отсутствие функции, а не пропущенный пункт перечня. В этом случае
   пробуют создавать инструмент самому: регистр `@mcp.tool()` сервера назван в шапке ответа
   `rules_functions.py`, контракт сторожит `python tools/check_mcp_tool_wiring.py`, правило правки
   кода MCP — карточка `rules:<слой>:functional:edit-mcp-code` того слоя, чей код правят (лист
   адреса общий для четырёх слоёв, адрес выводится из метки слоя).
3. Функций под задачу нет — это ответ о состоянии слоя, а не об отсутствии инструментов сервера: число
   инструментов называет регистр `@mcp.tool()` в шапке ответа `rules_functions.py`. Снимок прежних
   текстов слоя осматривают `rules_read.py --tree "rules:<слой>:journal:"` — снимок правилом не
   является, и искать в нём действующее правило нельзя.

### Намерение править код MCP-сервера

Задача звучит как «править код MCP», «изменить код MCP», «добавить инструмент», «продолжаем разработку MCP»,
«изменить инструмент», «убрать инструмент», «снять инструмент», «изменить состав инструментов», «поправить шаг поиска», «сменить формат выдачи», «правка DDL» — это намерение править код сервера, и оно поднимает карточку `rules:<слой>:functional:edit-mcp-code` до правки, а не после: карточка
задаёт порядок шагов (проверка, есть ли функция под задачу; регистр `@mcp.tool()`;
`EXPECTED_TOOLS`; перезапуск сервера; узел журнала о составе). Эти формулировки записаны алиасами карточек правки кода всех четырёх слоёв, список их задаёт `EDIT_CODE_INTENTS` в `src/rules_layer.py` одним местом, а прогон `tools/check_rules_layer.py` требует, чтобы каждая формулировка настоящим поиском вела в карточку своего подслоя (узел EDIT-CALL) — правка списка делается только там, где он задан. Слой берётся по файлу, которого касается правка: `server.py` — `kb-rules`, `server_configurations_core.py` — `core-rules`, `server_configurations_enrichment.py` — `enrich-rules`, `server_configurations_export.py` — `export-rules`; правка общего кода
(`src/mcp_tools_api.py`, `src/quarantine.py`, `src/schema.sql`) относится к слою того сервера, чьё поведение она меняет.

Перечень функций четырёх серверов целиком не читают: задача касается одного MCP. Функции слоя не перечисляются и в самой карточке слоя: карточку читают целиком, и с перечнем детей она тяжела для всегда загружаемого набора (замер узла FUNC-SEARCH: карточка слоя давала с блоком на 4 059 симв. больше, чем без него). Порог `ALWAYS_BUDGET_CHARS` — 18 000 симв. (поднят узлом D4 по замеру 27.10.2026: всегда читаемый набор политики — `rules:` 5600 и `rules:kb-rules:` 11 341, итого 16 941 симв.; always-состояние корневого слоя при этом даёт 12 899 по четырём карточкам `rules:always:*` — это другая величина, путать их нельзя). Чем мерить бюджет и почему порог именно такой — карточка `rules:checks:always-budget`; снимок состава даёт `python tools/_rules_check_snapshot.py`. Блок снят узлом FUNC-SEARCH.

### Что загружается всегда, а что вариативно

ВСЕГДА — константа `ALWAYS_ADDRESSES` в `tools/rules_read.py`, выдаётся одним `--always`:

- `rules:` — корень дерева: карта слоёв, формат адреса, порядок чтения и правки;
- `rules:kb-rules:` — слой `1c-knowledge-base`: общие записи работы со слоем знаний (искать в базе прежде ответа по памяти, называть категорию, покрывать алиасы, карантин, чтение содержимого адресом). Они действуют при любой задаче и одинаковы для трёх других MCP-серверов, поэтому читаются до начала работы.

ВАРИАТИВНО — слой поднимают, только когда задача касается его назначения (описания печатает
`--layers`, они же лежат в индексных карточках слоя):

| слой | общее назначение — когда нужен |
|---|---|
| `rules:core-rules:` | загрузка выгрузок 1С: конфигурация, внешние отчёты и обработки, `.erf`/`.epf`, каталоги XML-выгрузки |
| `rules:enrich-rules:` | обогащение уже загруженного объекта: алиасы, сниппеты, макеты, кросс-ссылки, витрины обогащения |
| `rules:export-rules:` | реверс-инжиниринг: сборка изменённого объекта обратно в XML |

Все четыре слоя лежат в дереве: общие записи — карточка второго уровня `rules:<слой>:`, функции —
`rules:<слой>:functional:<функция>`, предписания инструментов регистра —
`rules:<слой>:<инструмент>-tool` (имя инструмента в адресе пишется через дефис). Снимок прежних
текстов — ветка `journal` каждого слоя, её индекс — `rules:<слой>:journal:index`; снимок действующим
правилом не является. Живое дерево трёх конфигурационных слоёв сверяет
`python tools/_layer_tree_check.py` (карточка на каждый инструмент регистра, обязательные разделы, теги
вида, отсутствие ссылок на прежние адреса, полнота `===INDEX`); состав слоя показывают
`python tools/_layer_ls.py rules:<слой>:` и `--layers`/`--tree` читателя правил.

### Снимок дерева и правки

Текущее состояние дерева видно дампом:

```powershell
python src/rules_report.py --query rules    # корневая карточка и верхний слой правил
python src/rules_report.py --query rules:   # одна корневая карточка (выбор по алиасу уровня)
```

Правки делаются строками БД (`knowledge_snippets.question` = адрес, `answer` = содержимое), а не
этим файлом. Файл — правила работы ассистента и точка входа в дерево правил.
