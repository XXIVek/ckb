## 📚 Правила работы с MCP-серверами — в базе `local_doc`

Правила четырёх MCP-серверов (`1c-knowledge-base`, `1c-configurations-core`,
`1c-configurations-enrichment`, `1c-configurations-export`) живут строками базы `local_doc`, а не в этом файле. Здесь остаются правила работы ассистента: роль, терминал, вывод.

### Чем читают правила

`python tools/rules_read.py` — инструмент чтения набора правил (узел RULE-READ). Поиском MCP
правила не читают: `search_docs_tool` отдаёт id, заголовок и превью в 200 символов, потому что
его алиасные и полнотекстовые шаги не гарантируют единственности ответа. Адрес карточки —
уникальный ключ, двумя адресами две карточки не описываются, поэтому правило чтения другое:

| запрос | что отдаёт |
|---|---|
| `--always` | полный текст того, что читается всегда (перечень ниже) |
| `--layers` | список слоёв: политика загрузки, назначение, число карточек, объём |
| `"rules:kb-rules:"` | родительскую карточку целиком, детей — списком адресов |
| `"rules:kb-rules:checks:index"` | одну карточку целиком, без усечения |
| `--tree <адрес>` | только перечень адресов поддерева, без содержимого |
| `find карант` | одна найденная карточка — целиком; несколько — таблица адресов |
| `--marked` | то же плюс строки, помечённые к удалению (узел Q1), с причиной |

Карточки, помечённые к удалению, по умолчанию не отдаются: скрытая строка не является правилом.
Инструмент только читает — правки делаются строками БД.

### Если при выполнении задачи не хватает функциональности MCP

Сначала проверяют функции того MCP, с которым идёт работа, — поиск всегда с указанием сервера:

```powershell
python tools/rules_functions.py 1c-knowledge-base          # функции сервера: адрес + ===WHEN===
python tools/rules_functions.py kb-rules --term карантин    # есть ли функция под задачу
```

1. Функция найдена — её правило читают целиком адресом: `python tools/rules_read.py "<адрес>"`.
2. Функции под задачу нет — это отсутствие функции, а не пропущенный пункт перечня. В этом случае
   пробуют создавать инструмент самому: регистр `@mcp.tool()` сервера назван в шапке ответа
   `rules_functions.py`, контракт сторожит `python tools/check_mcp_tool_wiring.py`, правило правки
   кода MCP — карточка `rules:kb-rules:functional:edit-mcp-code`.
3. Функций под задачу нет — это ответ о состоянии слоя, а не об отсутствии инструментов сервера: число
   инструментов называет регистр `@mcp.tool()` в шапке ответа `rules_functions.py`. Снимок прежних
   текстов слоя осматривают `rules_read.py --tree "rules:<слой>:journal:"` — снимок правилом не
   является, и искать в нём действующее правило нельзя.

Перечень функций четырёх серверов целиком не читают: задача касается одного MCP. Функции слоя не перечисляются и в самой карточке слоя: карточку читают целиком, и с перечнем детей она весела за бюджет always (14 994 симв. при ALWAYS_BUDGET_CHARS = 12 000; без блока — 10 935). Блок снят узлом FUNC-SEARCH.

### Что загружается всегда, а что вариативно

ВСЕГДА — константа `ALWAYS_ADDRESSES` в `tools/rules_read.py`, выдаётся одним `--always`:

- `rules:` — корень дерева: карта слоёв, формат адреса, порядок чтения и правки;
- `rules:kb-rules:` — слой `1c-knowledge-base`: общие записи работы со слоем знаний (искать в базе прежде ответа по памяти, называть категорию, покрывать алиасы, карантин, чтение содержимого адресом). Они действуют при любой задаче и одинаковы для трёх других MCP-серверов, поэтому читаются до начала работы.

ВАРИАТИВНО — слой поднимают, только когда задача касается его назначения (описания печатает
`--layers`, они же лежат в индексных карточках слоя):

| слой | общее назначение — когда нужен |
|---|---|
| `rules:core-rules:` | загрузка выгрузок 1С: конфигурация, внешние отчёты и обработки, `.erf`/`.epf`, каталоги XML-выгрузки |
| `rules:enrich-rules:` | обогащение уже загруженного объекта: алиасы, сниппеты, макеты, кросс-ссылки, витрины обогащения |
| `rules:export-rules:` | реверс-инжиниринг: сборка изменённого объекта обратно в XML |

Все четыре слоя лежат в дереве: общие записи — карточка второго уровня `rules:<слой>:`, функции —
`rules:<слой>:functional:<функция>`, предписания инструментов регистра —
`rules:<слой>:<инструмент>-tool` (имя инструмента в адресе пишется через дефис). Снимок прежних
текстов — ветка `journal` каждого слоя, её индекс — `rules:<слой>:journal:index`; снимок действующим
правилом не является. Живое дерево трёх конфигурационных слоёв сверяет
`python _layer_tree_check.py` (карточка на каждый инструмент регистра, обязательные разделы, теги
вида, отсутствие ссылок на прежние адреса, полнота `===INDEX`); состав слоя показывают
`python _layer_ls.py rules:<слой>:` и `--layers`/`--tree` читателя правил.

### Снимок дерева и правки

Текущее состояние дерева видно дампом:

```powershell
python src/rules_report.py --query rules    # корневая карточка и верхний слой правил
python src/rules_report.py --query rules:   # одна корневая карточка (выбор по алиасу уровня)
```

Правки делаются строками БД (`knowledge_snippets.question` = адрес, `answer` = содержимое), а не
этим файлом. Файл — правила работы ассистента и точка входа в дерево правил.
