# Правила загрузки документации в 1C Knowledge Base

## СТРУКТУРА БАЗЫ ДАННЫХ

| Таблица | Назначение | Что хранить |
|---------|-----------|-------------|
| groups | Группы справки (иерархическая структура) | name, parent_id, description, tags |
| elements | Элементы справки (подчинены группам) | name, content, tags, group_id |
| search_aliases | Поиск по синонимам | alias_name, target_type (group/element/snippet), target_id, weight |
| knowledge_snippets | Сниппеты кода | question, answer, source_url, tags, confidence, element_id |
| doc_tags | Теги классификации | code, name, description, weight |

> **Важно:** Таблицы `docs` и `doc_fragments` удалены. Вся загрузка идёт через группы → элементы → сниппеты.

## ИСТОЧНИК ДАННЫХ ДЛЯ ЗАГРУЗКИ

Путь к каталогу с файлами указывается пользователем в задании на загрузку:

```text
Загрузка из: C:\1C_LLM\LoadDoc\html\BSL

Примерная структура файлов (может отличаться):

C:\1C_LLM\LoadDoc\
├── html\                    ← HTML-документация
│   ├── BSL\                ← БСЛ (объекты, типы, методы)
│   │   ├── objects\        ← описания объектов платформы
│   │   │   ├── Global context.html
│   │   │   ├── catalog*.html
│   │   │   └── catalogXXX\ ← подкаталоги с методами/свойствами/событиями
│   │   └── tables\         ← таблицы данных
│   └── its\                ← материалы портала ИТС
├── pdf\                    ← PDF-документация (Главы 1-39, Приложения)
└── markdown\               ← Markdown-файлы (при наличии)
```

> **Важно:** Файлы документации хранятся во внешнем каталоге `C:\1C_LLM\LoadDoc`, а не в проекте. Это предотвращает попытку отслеживания тысяч файлов в Git и экономит место репозитория.

### Почему файлы НЕ в проекте

- **Объём:** ~50 000+ HTML-файлов + 53 PDF (~1 ГБ)
- **Git не предназначен** для хранения бинарных файлов и больших объёмов данных
- **Тормозит работу:** каждый `git status`, `git add`, `git push` будет работать минуты

### Как работает загрузка

1. Пользователь задаёт путь к каталогу в задании (например, `C:\1C_LLM\LoadDoc\html\BSL`)
2. AI анализирует структуру папки и содержимое файлов
3. Определяет формат и методику фиксации информации
4. Загружает данные через MCP-инструменты

## КОНЦЕПЦИЯ ЗАГРУЗКИ (алгоритм принятия решений)

При получении задания на загрузку AI выполняет следующие шаги:

### Шаг 1: Анализ источника данных

Определяет тип входных данных:

- **HTML-файлы** — документация, справочные материалы, методы/свойства/события
- **PDF-файлы** — главы документации (Глава 4 Встроенный язык и т.д.)
- **Markdown-файлы** — структурированная документация
- **Прямой текст** — вопрос-ответ, описание метода

### Шаг 2: Определение формата контента

Анализирует содержимое каждого файла/блока:

| Признак | Методика фиксации | Инструменты |
|---------|-------------------|-------------|
| Вопрос + ответ с примером кода | **Сниппет** (`knowledge_snippets`) | `add_snippet_tool` |
| Структурированный документ (описание типа, метода, свойства) | **Группы → Элементы** (`groups` → `elements`) | `create_group_tool`, `create_element_tool` |
| Каталог каталогов (иерархия объектов) | **Иерархия групп** (`groups` с `parent_id`) | `create_group_tool(parent_id=...)` |
| Простое описание без кода | **Элемент** (`elements`) | `create_element_tool` |

### Шаг 3: Выбор стратегии загрузки

#### Сценарий A: Файлы BSL (объекты платформы)

```text
HTML-файл → Определение типа (метод/свойство/событие)
            ↓
    Есть ли пример кода? → Да → Создать элемент + сниппет
                           Нет → Создать только элемент
            ↓
    Есть родительский каталог? → Да → Привязать к группе
                               Нет → Создать корневую группу
```

#### Сценарий B: PDF-документация (главы)

```text
PDF → Извлечение текста → Определение структуры
      ↓
  Разбиение на разделы/подразделы
      ↓
  Каждый раздел → элемент с тегами
  Примеры кода → сниппеты
```

#### Сценарий C: Markdown-документация

```text
Markdown → Парсинг заголовков → Определение иерархии
           ↓
       Каждый раздел h2/h3 → группа или элемент
       Примеры кода → сниппеты
    ```       

### Шаг 4: Фиксация в БД

Для каждого элемента применяется методика из таблицы выше. При этом:
- **Алиасы** создаются автоматически при создании группы/элемента
- **Теги** определяются по содержимому (используется `detect_tags_tool`)
- **Категория** определяется по контексту (language/platform/its/methodology)

## ЗАГРУЗКА ЧЕРЕЗ MCP-ИНСТРУМЕНТЫ

### Группы

```text
create_group_tool(name, parent_id?, description?, tags?)    → создать группу
update_group_tool(group_id, name?, description?, tags?)     → обновить группу
get_group_hierarchy_tool(group_id?)                         → дерево групп
search_groups_tool(query, limit=20)                         → поиск групп
```

### Элементы

```text
create_element_tool(group_id, name, content?, tags?)        → создать элемент
update_element_tool(element_id, name?, content?, tags?)     → обновить элемент
get_element_details_tool(element_id)                        → детали + сниппеты
search_elements_tool(query, limit=20)                       → поиск элементов
```

### Сниппеты

```text
add_snippet_tool(question, answer, source_url?, tags?, confidence?, element_id?)  → добавить
fix_snippet_tool(snippet_id, new_question?, new_answer?, reason)                  → исправить
search_snippets_tool(query, limit=20)                                               → поиск
```

### Утилиты

```text
detect_tags_tool(text)        → определить теги по тексту
get_load_rules_tool()         → получить эти правила
get_db_state_tool()           → состояние БД (количество записей)
```

## ПРИМЕР ПОЛНОЙ ЗАГРУЗКИ (один метод из BSL)

### Шаг 1: Создать группу (если нет)

```python
create_group_tool(
    name="Глобальный контекст",
    description="Функции глобального контекста БСЛ",
    tags="language,global_context"
)
# → возвращает group_id = 5
```

### Шаг 2: Создать элементы (метод + свойства)

```python
create_element_tool(
    group_id=5,
    name="ПолучитьОбъект",
    content="Синтаксис: ПолучитьОбъект(Тип)\n\nОписание: Возвращает ссылку на объект указанного типа.\n\nДоступность: Серверное приложение.",
    tags="language,api,method"
)
# → возвращает element_id = 12

create_element_tool(
    group_id=5,
    name="СоздатьОбъект",
    content="Синтаксис: СоздатьОбъект(Имя)\n\nОписание: Создаёт COM-объект.",
    tags="language,api,method"
)
# → возвращает element_id = 13
```

### Шаг 3: Добавить сниппеты (примеры кода)

```python
add_snippet_tool(
    question="Как создать объект Справочник.Номенклатура?",
    answer="Спр = СоздатьОбъект('Справочник.Номенклатура');\nСпр.НайтиЭлемент('Товар1');",
    tags="code,api",
    confidence=0.9,
    element_id=13
)

add_snippet_tool(
    question="Как получить объект по типу?",
    answer="Объект = ПолучитьОбъект('Справочник.Номенклатура');\nОбъект.ПолноеНазвание;",
    tags="code,api",
    confidence=0.9,
    element_id=12
)
```

### Шаг 4: Проверить результат

```python
get_db_state_tool()     # проверить количество записей
search_elements_tool("ПолучитьОбъект")  # найти элемент
get_element_details_tool(12)            # детали + сниппеты
```

## МЕТРИКИ КАЧЕСТВА ЗАГРУЗКИ

| Метрика | Минимум |
|---------|---------|
| Групп на раздел BSL | >= 3 (типы данных, объекты конфигурации, глобальный контекст) |
| Элементов на группу | >= 5 (для крупных групп) |
| Алиасов на каждый элемент | >= 3 |
| Сниппетов на элемент с примерами кода | >= 1 |
| Тегов на элемент | >= 2 |

## ВАЖНЫЕ ЗАМЕЧАНИЯ

1. **Нет таблиц `docs` и `doc_fragments`** — загрузка только через `groups` → `elements` → `snippets`
2. **Алиасы создаются автоматически** при создании группы/элемента (из имени). Дополнительные можно добавить через SQL напрямую.
3. **Теги определяйте вручную** по содержимому файла: используйте `detect_tags_tool(text)` для проверки
4. **Путь к файлам всегда задаётся в задании** — он не зафиксирован, может быть любым
5. **Структура папок произвольная** — пример в разделе «ИСТОЧНИК ДАННЫХ» приведён только как ориентир
6. **Не загружайте** пустые файлы без контента и служебные файлы (`__categories__`, каталоги)
